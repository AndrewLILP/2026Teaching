Asking a good data question

Every useful analysis starts with a good question. "Is my game too hard?" sounds like a question, but the data can't answer it until it's made specific and measurable. Today you'll learn to sharpen questions, break them into parts, and work out who needs the answer.

Identifying & defining

Teaching advice

Timing: hook 4 min · vocabulary 5 min · judge the questions 10 min · anatomy 6 min · break it down 8 min · users 5 min · Cave of Echoes 7 min · tasks 5 min · checkpoint and exam question 5 min.

Discussion focus: the key move is from "Is it good?" to a question that names fields in the data. Keep asking: which column would answer that? If no column exists, the question can't be answered with this data, which is a useful finding too.

Keep handy: the column headings from Lesson 1 (Five rows, five systems). Students need them to judge whether a question is answerable.

Learning intentions

By the end of this lesson I can:

  • turn a vague concern into a data question that the available data can answer
  • break a large data question into smaller sub-questions linked to fields
  • describe the users of a data analysis and the decision they need to make.
Success criteria: I can write one data question for a project, break it into at least three sub-questions, and name the field or fields that answer each one.

Is the game too hard?

The developer of Coin Run 3D has 155 run records and one worry: "I think my game is too hard." She opens the data file and stares at it. Where should she start?

Talk with the person next to you. "Too hard" for whom? On which level? How would you know from the data? Try to rewrite her worry as a question the file could answer.

  • What percentage of runs are completed on each level?
  • How many deaths happen on average on each level?
  • Do Steam Deck runs complete less often than PC runs?

Each rewrite names something we can count or measure using a column in the data (completed, deaths, platform, level). "Too hard" can't be counted. "Percentage of Level 3 runs completed" can.

Analysis first

Judge the questions

People asked these questions about our five projects. Before learning any rules, sort each one. Use the column headings from Lesson 1 to check whether the data could answer it.

  • Good data question: specific, and the data has the fields to answer it.
  • Too vague: it's not clear what to count or compare.
  • Data can't answer: it's specific, but the dataset doesn't record what's needed.

  1. Which Canteen Click item sells the most on Fridays?

  2. Is the canteen any good?

  3. Do students enjoy the food they order?

  4. Do Cave of Echoes sessions with more invalid commands end in Quit more often?

  5. Which room do Cave of Echoes players quit in?

  6. What's going on with Pixel Pockets?

  7. Does using StepUp make people healthier?

  8. In which week do StepUp workouts drop the most?

  9. Why is Cave of Echoes boring?

  10. Do Steam Deck runs on Level 3 finish less often than PC runs?

What makes a good data question

A good data question passes three checks. If it fails one, rewrite it before you touch the data.

Three checks for a data question
CheckAsk yourselfFailsPasses
SpecificDoes it say what, who and when?Is the canteen busy?How many orders are placed on each day of the week?
MeasurableWhich fields answer it? Can they be counted, averaged or compared?Do players like Level 2?What percentage of Level 2 attempts are cleared?
UsefulWho will use the answer, and what will they decide?What is the average playerId?Where on Level 2 do most failed attempts end, so we know which jump to fix?

Sentence frame

"[User] wants to know [measurable thing] for [which records / time] so they can decide [decision]."

Break it down

Real questions are usually too big to answer in one step. Analysts use decomposition: split the big question into sub-questions, and link each sub-question to the fields that answer it.

Worked example: Canteen Click Big question How much stock should the canteen prepare for Fridays?
Sub-questions and fields for the Canteen Click Friday question
Sub-questionFields neededProcessing
1. Are Fridays busier than other days?orderDateCount orders per day
2. Which items sell most on Fridays?orderDate, itemId, quantityFilter to Fridays, total quantity per item
3. Is the Friday demand at recess or lunch?orderDate, pickupFilter to Fridays, count by pickup
4. Were any Friday totals inflated by one big order?orderDate, quantityFilter to Fridays, sort by quantity, look for unusual values

Sub-question 4 matters. On the Friday in our dataset, beef burgers sold 22 and sausage rolls sold 19. But 12 of those sausage rolls came from one order for a class event. Without sub-question 4, the canteen would prepare far too many sausage rolls for a normal Friday.

Who uses the answer?

The user of a data analysis is the person who makes a decision from it. That's often not the person whose data is being analysed. Knowing the user tells you what form the answer should take.

Users of the analysis and people in the data for each project
ProjectUser of the analysisWhat they needPeople in the data
Coin Run 3DLevel designerWhich level, and which platform, to fix firstPlayers
Cave of EchoesSolo Python developerWhich commands confuse playersPlayers
StepUpProduct teamWhen users stop exercising, so they can send a reminderApp users
Pixel PocketsProducer and level designerWhere players fail on each levelPlaytesters
Canteen ClickCanteen managerA simple stock list, not a spreadsheetStudents who order

The canteen manager might never open a spreadsheet. So her answer should be a short list of how many of each item to prepare, not a table of 176 orders.

We do: why do players quit?

We do · whole class · 7 min

The Cave of Echoes developer asks: "Why do players quit my game?" The data has these fields:

sessionId, playerId, turns, validCommands, invalidCommands, roomsVisited, ending, minutesPlayed

  1. Which of the three checks does the question fail?
  2. Write three sub-questions that the fields can answer.
  3. Write one sub-question the developer would love to answer but can't with this data. What field is missing?

1. It's not measurable yet. "Why" can't be counted directly, but we can look for patterns linked to quitting.

2. Do sessions with more invalid commands end in Quit more often? · Do players who quit visit fewer rooms than players who escape? · Do players quit earlier in their first session than in later sessions?

3. "Which command did players type just before quitting?" The data records a count of invalid commands, not the commands themselves. To answer this, the game would need to log each command, which also raises a privacy question if players type personal information.

Core

Decompose a question

Choose Coin Run 3D or StepUp. Write one big data question using the sentence frame.

  • Break it into at least three sub-questions.
  • For each, list the fields needed and the processing.
  • Name the user and their decision.
Extension

Find the gaps

Write a big question for your own game or app, then decompose it.

  • Identify at least one data gap, and the field you'd need to add.
  • Explain whether collecting that field is worth any privacy risk.

Checkpoint

Exam-style question

Short answer 4 marks

A Coin Run 3D developer says: "I want to know if my game is too hard." Each run record contains runId, playerId, level, coinsCollected, coinsAvailable, timeSeconds, deaths, completed, platform.

Question: (a) Explain why the developer's statement is not yet a good data question. (2 marks) (b) Rewrite it as a data question the run data can answer, and identify two fields needed to answer it. (2 marks)

Write your answer in your notebook before opening the marking guide.

Marking guide
CriteriaMarks
(a) Explains that "too hard" is vague/not measurable AND that it doesn't say which level, platform or what to count2
(a) Identifies that the statement is vague or not measurable1
(b) Writes a specific, measurable question AND names two relevant fields2
(b) Writes a measurable question OR names two relevant fields1

Sample answer: (a) "Too hard" can't be measured directly. It doesn't say which level or platform, or what would show that the game is hard, so the analyst doesn't know what to count. (b) What percentage of runs are completed on each level? This needs the level and completed fields.

Common error: naming a field that doesn't match the question, such as coinsCollected for a completion question, or rewriting the question as "Is Level 3 hard?", which is still not measurable.
