Lesson 4 of 25 · 55 minutes

What must the analysis do?

A vague request like "make me a report" leads to two people building two different things. Today you'll pin down exactly what a data analysis must do: its purpose, its functional requirements, a use case, and test cases that prove it works.

Identifying & defining

Teaching advice

Timing: hook 3 min · vocabulary 5 min · deconstruct 7 min · purpose and requirements 8 min · use case 7 min · test cases 12 min · sort 4 min · tasks 4 min · checkpoint and exam question 5 min.

Discussion focus: test cases are the heart of this lesson. Make students work out each expected output by hand from the eight test rows before revealing it. The boundary row (A6, x = 1400) and the TEST row (A8) are deliberate traps.

Note: functional requirements here describe what the analysis must do, not what the game must do. Students who built games may slip back into game features.

Learning intentions

By the end of this lesson I can:

  • state the purpose of a data analysis solution
  • write functional requirements and a use case for a data analysis
  • develop test cases with inputs and expected outputs, including boundary cases.
Success criteria: For one data analysis I have written a purpose statement, at least three functional requirements, a use case with an alternative flow, and three test cases with expected outputs I worked out by hand.

"Make me a report"

After a playtest, the Pixel Pockets producer sends the team one line: "Make me a report about where players fail."

Two developers build it separately. One makes a list of every failed attempt. The other makes a bar chart of failures by position on the level. Both say they did what was asked. Who's right? What should the producer have written instead?

Analysis first

Deconstruct a summary

Before writing requirements, look at what a finished analysis does. This is the weekly summary card a StepUp user sees on Sunday night.

StepUp · your week 4 workouts · 162 minutes in total
Most common activity: Walk
Busiest day: Saturday
2 fewer workouts than last week

Analysis activity · pairs · 7 min

What must the system do to produce this?

  1. For each line on the card, write what the system had to do to produce it. Start each with a verb: count, total, find, compare.
  2. Which fields from the workout records did each line need? (workoutId, userId, date, activity, durationMin, distanceKm, steps, avgHeartRate)
  3. Which line needs data from two different weeks?
  4. What should the card show if the user did no workouts this week?

1 and 2. Count this user's workouts in the week (userId, date) · total durationMin · find the most frequent activity · find the day with the most workouts (date) · compare this week's count with last week's.

3. "2 fewer workouts than last week" needs last week's count as well.

4. That's an alternative flow. A sensible output is "No workouts this week. Ready to start again?" rather than "0 minutes, most common activity: (blank)".

Each answer to question 1 is a functional requirement: something the analysis must do.

Defining

Purpose statement

Back to the Pixel Pockets producer. A purpose statement fixes the vague request by naming the user, what the solution does and the decision it supports.

Purpose: Pixel Pockets fail report The fail report helps the level designer see where on each level playtesters fail, so they can choose which section to redesign before the next playtest.

Now the two developers can check their work against it. The list of every failed attempt doesn't show where failures cluster, so it doesn't meet the purpose. The bar chart does.

Functional requirements

Functional requirements list exactly what the analysis must do. Each one should be specific enough to test.

Functional requirements for the Pixel Pockets fail report
IDThe fail report must…
FR1load an attempts file with the columns attemptId, playerId, level, coins, jumps, timeSeconds, outcome, endX
FR2exclude test records (playerId = TEST)
FR3for a chosen level, count failed attempts (any outcome except Cleared) in 200-pixel bands of endX: 0–199, 200–399 and so on
FR4show the percentage of attempts cleared for the chosen level
FR5highlight the band with the most failed attempts

Not a requirement of the analysis

"Players can double jump" is a requirement of the game. Today we're writing requirements for the analysis of the game's data.

Use cases

A use case shows how a user reaches one goal, step by step. It also shows what happens when things go wrong.

Use case: find where players fail on a level
Use case: Level designer finds where players fail on a level
ActorLevel designer
Main flow1. Designer opens the fail report.
2. Designer loads the latest attempts file.
3. Designer chooses Level 2.
4. Report removes test records and counts failed attempts in each band.
5. Report shows a bar chart with the busiest band highlighted, and the cleared percentage.
6. Designer notes the band to redesign.
Alternative flow 2aThe file is missing the endX column. The report names the missing column and stops.
Alternative flow 3aNo attempts are recorded for the chosen level. The report shows "No attempts recorded for Level 2".

Test cases

How do we know the report is correct? We give it a small input where we already know the answer. If we tested it on all 127 real attempts, we couldn't check the output by hand.

Here is the test input: eight attempts, chosen on purpose.

Work out the expected output for each test case by hand, before opening the answers. Watch out for A6 and A8.

Test cases for the fail report
IDChecksInputExpected output
TC1FR3All eight rows, Level 2Count in band 1400–1599 = ______
TC2FR3 boundaryA6 only (endX = 1400)A6 is counted in band ______
TC3FR2All eight rows, Level 2Is A8 counted? ______
TC4FR4All eight rows, Level 2Cleared percentage = ______
TC5FR3All eight rows, Level 1Count in band 1400–1599 = ______

TC1: 3. A1 (1491), A3 (1522) and A6 (1400). A4 is Level 1, A2 was cleared and A8 is a test record.

TC2: 1400–1599. Bands start at 1400, so 1400 belongs to the band that starts there, not the one that ends at 1399.

TC3: No. FR2 excludes test records. If your TC1 answer was 4, you counted A8.

TC4: 16.7%. There are six real Level 2 attempts (A1, A2, A3, A5, A6, A7), and one of them (A2) was cleared: 1 ÷ 6 = 16.7%.

TC5: 1. Only A4 is a Level 1 attempt.

If the report gives a different output from the expected one, the test fails, and that's useful: it shows exactly which requirement has a bug.

Sort it out

These lines come from the planning documents for a Coin Run 3D completion report. Is each one a functional requirement, a use case step or a test case?

  1. The report must show the completion percentage for each level.

  2. 3. The designer chooses "Steam Deck only" from the platform filter.

  3. Input: three Level 1 runs, two completed. Expected output: 66.7%.

  4. Input: one run with platform "steamdeck" in lower case. Expected: counted as SteamDeck.

  5. The report must exclude runs where coinsCollected is more than coinsAvailable.

  6. The report must let the user filter runs by platform.

  7. 4a. No runs match the filter. The report shows "No runs found".

  8. Input: no runs at all. Expected output: "No runs found", not 0%.

Your task

Choose the level that challenges you. You can move up a level once you finish.

Foundation

Expected outputs

Use the eight test attempts. Work out the expected output for:

  • Level 2, band 2400–2599
  • Level 2, band 600–799
  • Level 2, total failed attempts

Explain why A2 isn't counted in any of them.

Core

Plan a completion report

For a Coin Run 3D report that shows the completion rate for each level:

  • Write a purpose statement naming the user.
  • Write at least three functional requirements.
  • Write a use case with one alternative flow.
  • Write two test cases with tiny inputs.
Extension

Break the report

Design five test cases for the StepUp weekly summary card from this lesson.

  • Include a boundary case (a workout at 11:59 pm on Sunday) and an empty week.
  • Explain why test inputs should be small enough to check by hand.

Checkpoint

Answer all six. The first two are Foundation, the middle two are Core and the last two are Extension.

1. Which of these is a functional requirement for the Pixel Pockets fail report?
2. What does a test case contain?
3. Using the eight test attempts on this page, how many Level 2 failed attempts fall in band 1400–1599? Test records are excluded.
4. Why does the fail report's use case include an alternative flow for "no attempts recorded for this level"?
5. Bands in the fail report are 0–199, 200–399 and so on. Which single test input best checks the boundary between two bands?
6. Which is the best purpose statement for the Pixel Pockets fail report?

Exam-style question

Short answer 4 marks

The Canteen Click manager needs a report with this requirement: "For a chosen day, show the total quantity sold of each item." Use these four orders as test data:

Four test orders
orderIdorderDateitemIdquantity
O1Fri 5 MarM021
O2Fri 5 MarM0412
O3Fri 5 MarM022
O4Thu 4 MarM021

Question: (a) Write the main flow of a use case for the manager producing this report. Include at least three steps. (2 marks) (b) Write two test cases for the requirement, each with an input and an expected output. (2 marks)

Write your answer in your notebook before opening the marking guide.

Marking guide
CriteriaMarks
(a) Logical main flow of three or more steps, with the manager as actor, ending in the report output2
(a) Some relevant steps, or steps out of order1
(b) Two test cases, each with a specific input and a correct expected output2
(b) One correct test case, or two test cases missing expected outputs1

Sample answer: (a) 1. The manager opens the report. 2. The manager chooses Friday 5 March. 3. The report totals the quantity of each item ordered that day. 4. The report shows a list of items and totals. (b) TC1: input orders O1–O4, day = Fri 5 Mar. Expected output: M02 = 3, M04 = 12 (O4 is Thursday, so it's not included). TC2: input orders O1–O4, day = Mon 1 Mar. Expected output: "No orders for this day".

Common error: counting orders instead of totalling quantity (giving M02 = 2 and M04 = 1), or including O4 in Friday's total.
