Lesson 5 of 25 · 55 minutes

How well must it work?

A report can get every number right and still be slow, confusing or unsafe. Today you'll write the requirements that describe how well a data analysis must work, and turn vague words like "fast" and "secure" into targets you can test.

Identifying & defining

Teaching advice

Timing: hook 4 min · vocabulary 5 min · two reports 10 min · categories 8 min · make it testable 8 min · sort 5 min · case study 5 min · tasks 4 min · checkpoint and exam question 6 min.

Discussion focus: students write vague non-functional requirements ("fast", "easy", "secure"). The fix is always a number, a condition and a way to check it. Model the rewrite once, then make students do the rest.

Link back: Lesson 4's functional requirements for the Pixel Pockets fail report are reused in the make-it-testable section.

Learning intentions

By the end of this lesson I can:

  • explain the difference between functional and non-functional requirements
  • specify non-functional requirements for a data analysis, including usability, performance, reliability, security, privacy and accessibility
  • rewrite a vague requirement so it can be tested.
Success criteria: I can write four non-functional requirements for one data analysis, each with a measurable target and a way to test it.

Correct, but useless

The StepUp team builds the weekly summary card from Lesson 4. Every test case passes: the counts and totals are all correct. Then they release it.

  • The card takes 40 seconds to appear.
  • The text is too small to read on a phone.
  • A "friends" screen shows each friend's average heart rate.
  • When a user reaches 5,000 workouts, the card stops loading.

Talk with the person next to you. The card does everything it's meant to do. So what went wrong?

None of these problems is about what the card does. They're about how well it does it: speed, readability, privacy and coping with growth. Those qualities are non-functional requirements. If nobody writes them down, nobody tests them.

Analysis activity · pairs · 8 min

Why is B better?

  1. For each row of the table, write one word for the quality that makes B better (for example: speed, privacy).
  2. Which difference would matter most to the level designer? Which would matter most to a player?
  3. Report A shows more detail. Is more detail always better? When could it be worse?

1. Level 3 result: usability (readable precision, and the counts behind the percentage) · status: accessibility (colour alone fails colour-blind users) · detail: privacy (individual players aren't needed for this decision) · time to open: performance · runs on: portability and usability · blank platform: reliability.

2. The designer cares most about readability and speed. A player would care most about privacy: their own deaths, listed by ID.

3. No. Extra detail can expose personal data and hide the pattern the user needs. Show what the decision needs, and no more.

Kinds of non-functional requirement

Each kind can be written for any of our five projects. A good non-functional requirement includes a measurable target.

Non-functional requirement categories with examples
KindExample requirementHow to test it
PerformanceThe Canteen Click weekly report opens within 3 seconds for up to 2,000 orders.Load 2,000 test orders and time it.
UsabilityThe canteen manager can find Friday's best-selling item within 30 seconds, without training.Watch the manager try it, and time them.
ReliabilityRunning the Pixel Pockets fail report twice on the same file gives identical results.Run it twice and compare the outputs.
SecurityStepUp workout data is sent only over HTTPS.Inspect the network traffic during a sync.
PrivacyStepUp never shows one user's heart rate to another user.Log in as a friend and check every screen.
AccessibilityEvery Coin Run 3D chart labels its bars with text, not colour alone.View the chart in greyscale; check it with a screen reader.
ScalabilityThe Cave of Echoes analysis still runs when sessions grow from 143 to 100,000.Generate 100,000 test sessions and run it.

Make it testable

Vague requirements can't be tested, so nobody can prove they're met. A testable requirement has a measure, a target and a condition.

Worked example: Pixel Pockets fail report Vague The report should be fast. Testable The report shows the bar chart within 2 seconds (target) of choosing a level (measure: time), for a file of up to 5,000 attempts on a school laptop (condition).

We do · pairs · 6 min

Rewrite each vague requirement so it can be tested. Name the measure, target and condition.

  1. The Canteen Click report should be easy to use.
  2. StepUp should keep data secure.
  3. The Coin Run 3D report should work with lots of data.
  4. The Pixel Pockets chart should be accessible.
  1. A canteen staff member who hasn't used the report before can find the total sales for any day within 1 minute, without help.
  2. Workout data is encrypted when stored on the phone and in the cloud, and is sent only over HTTPS.
  3. The report opens within 5 seconds for files of up to 50,000 runs.
  4. Every bar has a text label and a value, and the chart has a text summary that a screen reader can read.

Your numbers may differ. What matters is that someone else could run the test and agree on whether it passed.

Sort it out

These are planning notes for the StepUp weekly summary card. Is each one a functional requirement, a non-functional requirement or a constraint on the project?

  1. The card shows the total minutes exercised this week.

  2. The card appears within 2 seconds of opening the app.

  3. The team has four weeks to build the card.

  4. No other user can see this user's heart rate.

  5. The card compares this week's workout count with last week's.

  6. All text on the card can be read at 200% zoom without overlapping.

  7. The card must be built with the app's existing database.

  8. The card names the most common activity this week.

Case study: 13 runs

Case study

Should we redesign Level 3 for Steam Deck?

The Coin Run 3D report shows Level 3 completion by platform. On PC, 20 of 41 runs were completed (48.8%). On Steam Deck, only 3 of 13 runs were completed (23.1%). The designer is ready to spend two weeks redesigning Level 3 for Steam Deck controls.

A teammate points out that 13 runs is very few. Three or four lucky or unlucky runs would change the Steam Deck percentage a lot. They suggest a new requirement: "Any percentage calculated from fewer than 20 records is marked 'small sample'."

Discuss: Is this a functional or a non-functional requirement? (You can argue either way.) Should the designer still act on the Steam Deck result? What data would make the decision safer?

Extension

Trade-offs

Some non-functional requirements pull against each other.

  • Explain how privacy and usefulness conflict in Report A vs Report B.
  • Find one other pair of qualities that conflict in one of the five projects, and recommend a balance.

Checkpoint

Answer all six. The first two are Foundation, the middle two are Core and the last two are Extension.

1. Which is a non-functional requirement for the Canteen Click weekly report?
2. "Every chart labels its bars with text, not colour alone." Which kind of non-functional requirement is this?
3. Which rewrite of "The fail report should be fast" can be tested?
4. StepUp passes every functional test, but friends can see each other's heart rate on a leaderboard. Which requirement has been missed?
5. On Level 3, Steam Deck runs completed 3 of 13 (23.1%) and PC runs 20 of 41 (48.8%). Which requirement best stops the designer from over-reacting?
6. Why are non-functional requirements often harder to test than functional ones?

Exam-style question

Short answer 4 marks

StepUp is a fitness app that records each user's workouts, including heart rate, and shows a weekly summary card.

Question: (a) Distinguish between functional and non-functional requirements, using an example of each for the StepUp weekly summary card. (2 marks) (b) Rewrite the requirement "The StepUp summary must be secure" so that it can be tested, and describe how you would test it. (2 marks)

Write your answer in your notebook before opening the marking guide.

Marking guide
CriteriaMarks
(a) Clearly distinguishes what the system does from how well it does it, with a correct StepUp example of each2
(a) Correct definition or a correct example of one type1
(b) Testable rewrite (measure/target/condition) AND a matching test2
(b) Improved but still partly vague rewrite, OR a test without a rewrite1

Sample answer: (a) A functional requirement describes something the card must do, such as "show the total minutes exercised this week". A non-functional requirement describes how well it must do it, such as "the card appears within 2 seconds of opening the app". (b) "Workout data, including heart rate, is sent from the phone to the cloud only over HTTPS and is stored encrypted." To test it, sync a workout while capturing network traffic and check that no workout data can be read in plain text.

Common error: giving two functional examples (for example, "show steps" and "show heart rate"), or rewriting "secure" as "very secure", which is still not testable.

What success looks like

These are the course performance descriptors for communicating with data. Tap a grade to see what it looks like in today's lesson.

A

Selects relevant data, media and processes to effectively communicate information in a range of contexts. Writes testable non-functional requirements and explains trade-offs between them, such as privacy versus detail.

B

Selects relevant data, media and processes to communicate appropriate information in a range of contexts. Writes four testable non-functional requirements of different kinds, each with a matching test.

C

Selects appropriate data, media and processes to communicate information in a range of contexts. Distinguishes functional from non-functional requirements and writes testable examples of each.

D

Uses data to communicate basic information. Names the quality broken by a described problem.

E

Uses data to communicate information in a very limited way. Identifies one way a report could be easier to read.
