Researching

Analyse a save file

Before designing our own data, let's look inside someone else's. This is part of the journal file from Ridgeline, the hiking game from Lesson 1. It holds two photos.

{
  "maxPhotos": 60,
  "entries": [
    {
      "fileName": "photo_20260914_101522.png",
      "caption": "Fog over the valley",
      "locationName": "Lookout Point",
      "timestamp": "2026-09-14T10:15:22"
    },
    {
      "fileName": "photo_20260914_103847.png",
      "caption": "",
      "locationName": "Creek Crossing",
      "timestamp": "2026-09-14T10:38:47"
    }
  ]
}

Analysis activity · pairs · 7 min

What does this file tell you?

  1. How many fields does each journal entry have? Name them.
  2. The second photo's caption is "". What does that tell you about captions?
  3. The photo itself isn't in this file. Where must it be, and how does the game find it?
  4. Look at how the file names are built. Why might the developers have used the date and time in each name?
  1. Four fields: fileName, caption, locationName and timestamp.
  2. Captions are optional. An empty string means "no caption yet", which is different from the field being missing.
  3. Each photo is saved as its own PNG file in the same folder. The game uses fileName to find and load it.
  4. Date and time give every photo a different name, as long as no two are taken in the same second (Lesson 4 handles that case). Names built year-first also sort into the order the photos were taken.
Planning

The data dictionary

A data dictionary records every design decision about our data in one place. Here is the dictionary for one JournalEntry record. Two cells are left for us to complete together.

FieldTypeExampleValidationRequirement
fileNameStringphoto_20261002_143012.pngMust end in .png and be uniqueR3
captionStringFog over the valleyTogether: ______R3
locationNameStringLookout PointMust match a named area in the gameR3
timestampTogether: ______2026-10-02T14:30:12Must be a valid date and timeR3

caption validation: 0 to 60 characters. Empty is allowed. Sixty characters fits on one line of the journal screen at Steam Deck resolution.

timestamp type: String, in ISO 8601 format (year-month-day, then time). Unity's built-in JSON tool, JsonUtility, can't save C# date values directly, so we store the date as text and convert it back when loading. Because the format puts the year first, sorting the strings also sorts the photos by date.

Worked example: why store the file name instead of the photo? The photo A 1920 × 1080 screenshot has 2,073,600 pixels. At 3 bytes per pixel that's 6,220,800 bytes, about 6.2 MB before compression. PNG compression usually makes game screenshots a few megabytes each. The record The four fields in one entry add up to roughly 150 characters, which is about 150 bytes. The decision If photos were inside journal.json, the game would have to read hundreds of megabytes just to show the journal's list. Storing file names keeps journal.json tiny, so it loads instantly, and photos are only loaded when they're needed.

We do · calculation · 3 min

A full journal holds 50 photos. Assume each PNG is 4 MB and each entry is 150 bytes.

  1. How much disk space do the photos use? (Answer in MB.)
  2. How big is journal.json? (Answer in KB, using 1 KB = 1,000 bytes.)
  3. How many times bigger is the photo storage than the JSON file? Round to the nearest thousand.
  1. 50 × 4 MB = 200 MB.
  2. 50 × 150 bytes = 7,500 bytes = 7.5 KB.
  3. 200 MB = 200,000 KB, and 200,000 ÷ 7.5 ≈ 26,667, so about 27,000 times bigger. This is why the photo limit in your requirements matters.
Planning

The capture algorithm

Now for the most important algorithm in the unit: what happens when the player presses capture. It's written in NSW pseudocode, so it doesn't depend on any programming language.

Look at lines 2 to 8 first. They are guard clauses: checks that stop the algorithm before it does any work. Putting every "should we stop?" check at the top is called the guard pattern. It keeps the main steps simple, because by line 9 we already know it's safe to continue.

NSW pseudocode · CapturePhoto

1   BEGIN CapturePhoto
2       IF photoModeActive = FALSE THEN
3           RETURN
4       ENDIF
5       IF journalCount >= maxPhotos THEN
6           DISPLAY "Journal full – remove a photo first"
7           RETURN
8       ENDIF
9       HIDE hud
10      SET image TO CaptureScreen()
11      SHOW hud
12      SET timestamp TO CurrentDateTime()
13      SET fileName TO "photo_" + FileSafe(timestamp) + ".png"
14      SAVE image TO fileName
15      SET entry TO NEW JournalEntry(fileName, "", currentLocation, timestamp)
16      ADD entry TO journalEntries
17      SET journalCount TO journalCount + 1
18      SAVE journalEntries TO "journal.json"
19  END CapturePhoto

Line 13: FileSafe turns 2026-10-02T14:30:12 into 20261002_143012, because colons aren't allowed in Windows file names. That gives photo_20261002_143012.png, matching the data dictionary.

The caption starts as an empty string (line 15). The player adds it later, which is why the data dictionary allows an empty caption.

Bug detective

The journal is full, but the disk keeps filling up

A classmate wrote this version. Their journal correctly stops at 50 entries, but playtesters' photo folders keep growing. Find the bug.

1   BEGIN CapturePhoto
2       HIDE hud
3       SET image TO CaptureScreen()
4       SHOW hud
5       SAVE image TO fileName
6       IF journalCount >= maxPhotos THEN
7           DISPLAY "Journal full – remove a photo first"
8           RETURN
9       ENDIF
10      ADD entry TO journalEntries
11  END CapturePhoto
The guard clause is in the wrong place. Line 5 saves the PNG before line 6 checks whether the journal is full, so every press creates a file that is never added to the journal. The HUD also flickers for no reason. The fix is the guard pattern: move the check to the top, before any work is done.
Designing

Storyboard for Steam Deck

Steam Deck's screen is 1280 × 800 pixels, about 7 inches across. That's the size to design for. If it works there, it will work on a monitor too. Here is a wireframe of the journal screen at that size.

#Design decisionWhyRequirement
1Photo count shown next to the titlePlayers can see when the journal is nearly fullJournal limit
2Thick, bright focus outline on the selected photoWith no mouse pointer, players must always see where they areR5 (gamepad only)
3Large detail panel with caption, location and dateShows every field from the data dictionary, at a readable sizeR3
4Button prompts that match the controllerPlayers never have to guess which button does whatR5, Steam Deck

Our design rule

No text smaller than 24 px on the 1280 × 800 wireframe. If you can't read it from arm's length on a printout scaled to 7 inches, make it bigger.

Your task

Data and screen

Core

Add a caption

  • Write AddCaption(entry, newCaption) in NSW pseudocode. Use a guard clause to reject captions over 60 characters.

  • Storyboard three screens: hiking, photo mode and journal, with arrows showing which button moves between them.
Extension

Delete a photo

  • Write DeletePhoto(entry) in NSW pseudocode. It must remove both the PNG file and the journal entry, and ask the player to confirm first.
  • Desk-check it, including the case where the PNG file is already missing.
  • Justify why timestamp is a string rather than a number of seconds since the game started.

Checkpoint

Answer all six. The first two are Foundation, the middle two are Core and the last two are Extension.

1. Why does the journal save each photo's file name in journal.json instead of the photo itself?
2. Which data type best suits the caption field?
3. CapturePhoto first checks IF photoModeActive = FALSE, then IF journalCount >= maxPhotos, before saving anything. What happens when photoModeActive is TRUE, journalCount is 50 and maxPhotos is 50?
4. What is the main purpose of a guard clause?
5. Unity's JsonUtility can't save C# date values directly. Which design is the best way to keep each photo's date and time?
6. A storyboard shows 24 thumbnails at once on a 1280 × 800 screen, each with its caption underneath. What is the strongest criticism for Steam Deck?
