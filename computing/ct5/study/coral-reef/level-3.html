Iteration: The Forever Loop

This example uses a Forever block with the Down Eye Sensor on the VR Robot to continually check for the blue boundary in order to avoid driving into the coral reef. When a blue boundary is detected, the VR Robot will back up and turn.

Playground: Coral Reef Cleanup Structure: Iteration + Selection Sensor: DownEye
CT5-OPL-01 CT5-THI-01 Iteration

Level 3 introduces the Down Eye Sensor inside a forever loop — the first true example of iteration in this series. The robot repeatedly drives forward and checks for the blue coral-reef boundary; every time it detects blue, it reverses and turns through a randomly chosen angle before continuing. This never stops (a "forever" loop), which is appropriate for an ongoing cleanup task.

3. NSW pseudocode

BEGIN
  REPEAT FOREVER
    DRIVE forward
    WAIT UNTIL DownEye detects blue
    DRIVE reverse 100 mm
    TURN right (RANDOM(90, 180)) degrees
  ENDREPEAT
END
Why this matters: pick random 90 to 180 is a random-number function — each loop iteration can produce a different turn angle. This means you cannot desk-check a single fixed outcome; instead you trace a range of possible values, which is exactly what happens in Section 4 below.

4. Python (VEXcode VR)

REPEAT FOREVER becomes Python's while True:, and pick random 90 to 180 becomes random.randint(90, 180) from Python's built-in random module.

level3_coral_reef_cleanup.py
import random

def main():
    while True:
        # Drive forward, collecting trash as it goes.
        drivetrain.drive(FORWARD)
        # Keep driving until the Down Eye Sensor detects blue.
        while not down_eye.detect(BLUE):
            wait(5, MSEC)
        # Back away from the coral reef boundary.
        drivetrain.drive_for(REVERSE, 100, MM)
        # Turn a random amount so the path never repeats exactly.
        drivetrain.turn_for(RIGHT, random.randint(90, 180), DEGREES)

vr_thread(main())
API notes: the outer while True: never exits — matching the forever block. The inner while not down_eye.detect(BLUE): is the same "wait until" pattern from Level 2, nested one level deeper.

Q6. Explain why pick random 90 to 180 is used instead of a fixed value like 135. (2 marks)

Show answer
A fixed angle could send the robot back toward the same boundary point repeatedly (or into a repeating pattern); randomising the turn makes the robot's escape path unpredictable, reducing the chance it gets stuck re-hitting the same boundary.
Extension B–A

Q7 — Debug. A student removed the drive reverse for 100 mm block, leaving only the turn. Explain the effect this bug would have. (3 marks)

forever
  drive forward
  wait until DownEye detects blue
  // drive reverse for 100 mm removed
  turn right for pick random 90 to 180 degrees
Show answer
Without reversing first, the robot is still touching (or very close to) the blue boundary when it turns, and driving forward again next iteration could immediately re-trigger the DownEye sensor or clip the reef edge — the reverse step creates clearance before the turn, which the bug removes.

Q8 — Extend. Design pseudocode for a Level 3b that also counts how many times the robot has bounced off the boundary, and prints a message after 5 bounces (without stopping the forever loop). (4 marks)

Show answer
BEGIN
  SET bounceCount = 0
  REPEAT FOREVER
    DRIVE forward
    WAIT UNTIL DownEye detects blue
    DRIVE reverse 100 mm
    TURN right (RANDOM(90,180)) degrees
    SET bounceCount = bounceCount + 1
    IF bounceCount = 5 THEN
      OUTPUT "5 boundary bounces reached"
    ENDIF
  ENDREPEAT
END
Credit responses that recognise a counter variable must be declared outside the loop (so it isn't reset each iteration) and only incremented inside the loop.
