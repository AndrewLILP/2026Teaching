Magic Numbers: One Request, Six Places to Fix

A one-line change request — "make it 10 rounds instead of 5" — exposes why typing the same value into code more than once is one of the most common sources of bugs in real software.

Artefact: Dice & Chance (MA4-PRO-C-01) Bug type: change request / maintainability DPM stages: Plan & Develop
CT5-DPM-01 Iterative process Magic numbers

Dice & Chance is a real browser-based probability teaching resource, built with two dice games: Push Your Luck (a banked-points game) and Dice Cricket (a batting simulation). This level is the first in a five-part series that follows the actual build-test-fix log of that project — real bug reports, real root causes, real fixes.

Outcome CT5-DPM-01 describes an iterative process with five stages: Define → Plan → Design → Develop → Evaluate. Every level in this series names which stage(s) broke down to cause the bug. This level is about what happens when Plan is skipped and a decision gets typed into Develop in more than one place.

1. The change request

Client note
Can we make each game run for 10 rounds instead of 5? Everything else can stay the same.

This sounds like a one-line fix. But when the code was searched, the number 5 had been typed in as a literal value in six separate places: the game-state object, two on-screen status labels, two end-of-game messages, and the "new game" reset handler.

push-your-luck.js (one of the six — before)
// The "5" is invisible to future-you and easy to miss
pylMsg.textContent = 'Game over! Final score after 5 rounds: ' + pyl.score + ' points.';

Try it yourself first

Open source/dice-games-buggy.html in your browser, then view its source (or open it in a text editor). Use Ctrl+F (or Cmd+F) to search the JavaScript for the literal number 5. Try to find all six locations before you reveal the list below. Note down what each one controls.

3. Root cause: magic numbers

Missing even one of these six locations would leave the game internally inconsistent — for example, displaying "Round 3 of 5" while the game logic actually allows 10 rounds to be played.

Concept for students — magic numbers: a value typed directly into code in multiple places, instead of stored once and referenced everywhere, is one of the most common sources of bugs in real software. A future change (like this one) has to be applied by hand, correctly, in every single location — and it only takes one miss to break the program.

The real fault here isn't a typo in the code that was written — it's a planning decision that was skipped. Deciding "the round count lives in exactly one place" is a Plan/Design decision, made before any code is typed. Skipping it doesn't cause an error straight away; it causes a maintenance trap that only goes off later, when someone has to change that value.

4. The fix: a single source of truth

The status labels and end-of-game messages were changed to read the round count from the game's own state (pyl.maxRounds, crik.maxInnings) instead of having the number typed in as literal text.

push-your-luck.js (after)
// One source of truth; changing pyl.maxRounds updates every message automatically
pylMsg.textContent = 'Game over! Final score after ' + pyl.maxRounds + ' rounds: ' + pyl.score + ' points.';

Now, changing the game length is a one-line edit to maxRounds, not a six-location hunt through the file. This is what "planning before developing" is meant to prevent: a decision made once, in one place, that every other part of the program reads from rather than repeats.

5. Practice questions

Foundation D–E

Q1. What change did the client actually ask for? (1 mark)

Show answer
Change both games from 5 rounds/innings to 10 rounds/innings.

Q2. How many separate places in the code had the number 5 typed in? Name two of them. (2 marks)

Show answer
Six places. Any two of: the game-state object, the two status labels, the two end-of-game messages, the "New Game" reset handler.

Q3. What would happen if a developer changed five of the six locations but missed one? (2 marks)

Show answer
The game would become inconsistent — e.g. it might actually allow 10 rounds of play, but a status label or message would still say "5", confusing the player.
Core C

Q4. Define the term magic number in your own words, and explain why it makes code harder to maintain. (3 marks)

Show answer
A magic number is a value typed directly into code in more than one place instead of being stored once and referenced everywhere. It makes code harder to maintain because any future change to that value must be found and applied correctly in every location by hand — missing even one introduces a bug.

Q5. Which stage of the CT5-DPM-01 iterative process (Define, Plan, Design, Develop, Evaluate) was skipped when the "5" was first written into six places, and which stage caught the resulting problem? (3 marks)

Show answer
Plan/Design was skipped — no single-source-of-truth decision was made before coding. Develop is where the fix was actually applied (reading from pyl.maxRounds instead of a literal).

Q6. Rewrite this line so the round count is read from a variable called maxRounds instead of being hardcoded: (2 marks)

before
statusLabel.textContent = 'Round ' + round + ' of 5';
Show answer
statusLabel.textContent = 'Round ' + round + ' of ' + maxRounds;
Extension B–A

Q7 — Evaluate. Describe a test you could run to prove all six locations now agree with each other, rather than just trusting that the fix worked. (3 marks)

Show answer
Change maxRounds to a different value (e.g. 7) and play a full game, checking that every status label, end-of-game message and the reset handler all reflect 7 rounds with no leftover "5" or "10" text anywhere. If all six update together from the one change, the single source of truth is genuinely in place.

Q8 — Extend. A future request asks for a "Marathon Mode" with a selectable round count (5, 10 or 20), chosen by the player before the game starts. Explain what would need to change in the Design stage to support this cleanly, given what you know about magic numbers. (4 marks)

Show answer
Nothing new needs to change in the messages or labels — they already read from maxRounds, so they'd automatically show whatever value is chosen. The Design stage would need to: add a selection control (e.g. a dropdown or buttons) before the game starts; set pyl.maxRounds from the player's choice instead of a fixed default; and confirm the reset handler re-reads that same value on "New Game" rather than assuming one fixed length. This shows the payoff of removing magic numbers early — the single-source-of-truth fix from this level directly enables this new feature with almost no extra work.
