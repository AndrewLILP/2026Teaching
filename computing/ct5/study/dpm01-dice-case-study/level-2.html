Dice & Chance · Iteration Case Study · Level 2

"I Need to Hit Refresh to Play Again"

A "Play Again" button that looked completely broken turned out to have perfect code. The real fault was one unguarded line, three functions away, that silently killed everything downstream of it.

Artefact: Dice & Chance (MA4-PRO-C-01) Bug type: unhandled exception DPM stages: Develop & Evaluate
CT5-DPM-01 Defensive programming Graceful degradation

This is the case study's central bug — the one that best shows the gap between "my code has an error" and "my code has a bug." Nothing in the code was written incorrectly. Every line did exactly what it was told. The bug only exists because of what was missing: a plan for what should happen when something outside the program's control — browser storage — fails.

1. The bug report

Player report
The "Play Again" button doesn't do anything. I have to reload the whole page to start a new game.

The report is a symptom, not a diagnosis — that's true of every real bug report. It names what the player saw, not what caused it. Finding the cause is the actual skill.

When the "Play Again" button's own code was checked line by line, it was completely correct. Simulating full games programmatically confirmed the reset logic worked perfectly — when everything else was working normally. So the bug wasn't in the button at all.

2. Investigate — reproduce it yourself

Try it yourself

Open source/dice-games-buggy.html in your browser and open Developer Tools (F12 or right-click → Inspect → Console). Paste this one line into the console and press Enter — it makes localStorage behave the way it does in some school devices, sandboxed previews, or private browsing:

localStorage.setItem = function(){ throw new Error('Storage blocked'); };

Now click on the die in either game a few times. What happens to the round counter? Does anything on screen respond at all? Try the "Play Again" button. Write down exactly what you observe before reading on.

3. Root cause: one unguarded call, three functions deep

The die-roll handler calls recordRoll() every roll, to log the result for the observed-vs-theoretical statistics further down the page:

dice-games-buggy.html (before)
// No error handling — if setItem throws, nothing below this line runs
function recordRoll(game, face){
  var c = getCount(game, face) + 1;
  localStorage.setItem(statsKey(game, face), String(c));   // ← throws here
  var t = getTotal(game) + 1;
  localStorage.setItem(totalKey(game), String(t));
}

In some environments — opening the file directly from disk instead of through a web server, private/incognito browsing, or a locked-down school device — localStorage throws an error instead of quietly failing. Because that call wasn't wrapped in a try/catch, the error doesn't just fail silently: in JavaScript, an uncaught error stops the entire rest of the current function from running, and unwinds back through everything that called it.

Trace stepWhat runs
1Player clicks the die
2Die-roll handler starts: generate face, update die display
3Handler calls recordRoll(game, face)
4🛑 localStorage.setItem(...) throws — recordRoll stops immediately
5Never runs: round counter increment
6Never runs: win/bust check
7Never runs: status label update, "Play Again" visibility logic
Concept for students — defensive programming and graceful degradation: code that depends on something outside its control (a file, a network connection, browser storage) should assume that thing can fail, and decide in advance what should happen when it does — rather than letting one failure cascade into an apparently unrelated part of the program. Refreshing the page only appeared to "fix" it because a refresh restarts the whole script from scratch, silently resetting the illusion each time.

4. The fix: contain the failure

The whole body of recordRoll was wrapped in a try/catch. If storage fails, the catch block runs instead of an uncaught error — and everything after the original call site (in the calling function) keeps executing normally.

dice-games-buggy.html (after — real code from the fixed file)
function recordRoll(game, face){
  // Wrapped so a storage failure (private browsing, file:// testing,
  // sandboxed preview, etc.) never breaks the game itself — it just
  // means this roll won't be added to the persisted tally.
  try{
    var c = getCount(game, face) + 1;
    localStorage.setItem(statsKey(game, face), String(c));
    var t = getTotal(game) + 1;
    localStorage.setItem(totalKey(game), String(t));
  } catch(e){ /* stats unavailable this session — gameplay continues normally */ }
}

Gameplay logic (the round counter, the win/bust check, the "Play Again" button) lives in the function that calls recordRoll — so once recordRoll can no longer throw past its own boundary, everything downstream of it runs normally every time, storage or no storage.

5. Proving the fix — not just eyeballing it

Try it yourself — confirm the fix

Open source/dice-games-fixed.html and repeat the exact same console trick from Section 2. Roll the dice again. This time, does the round counter still update? Does "Play Again" still work at the end of a game? If the only thing that changed is the file, and the only thing you did is the same console command, any difference in behaviour is the fix at work.

When this was fixed for real, a script (Node.js + jsdom) built a fake browser environment that deliberately made every localStorage call throw, then ran a full 10-round game through it programmatically. Before the fix, the game froze exactly as reported. After the fix, it completed all 10 rounds and "Play Again" worked — proving the storage failure could no longer affect gameplay, regardless of why storage had failed. That's the Evaluate stage of CT5-DPM-01 done properly: not "it looks fine now," but a repeatable test that would catch the bug again if it ever came back.

6. Practice questions

Foundation D–E

Q1. What symptom did the player report, in their own words? (1 mark)

Show answer
The "Play Again" button didn't seem to do anything — they had to reload the whole page to start a new game.

Q2. Was the bug actually inside the "Play Again" button's own code? Explain. (2 marks)

Show answer
No. The button's code was checked and found to be completely correct. The real fault was in a different function (recordRoll) that ran earlier and silently stopped everything after it.

Q3. What does try/catch do, in plain English? (2 marks)

Show answer
It lets a program attempt something that might fail (the try part) and run a backup plan instead of crashing if it does fail (the catch part).
Core C

Q4. Using the trace table in Section 3, explain in your own words why an error in recordRoll stopped the round counter from updating, even though the round counter code has nothing to do with localStorage. (3 marks)

Show answer
In JavaScript, an uncaught error stops the rest of the current function immediately and unwinds back through whatever called it. recordRoll was called partway through the die-roll handler, so when it threw an error with no try/catch, the rest of that same handler — including the round counter update — never ran, even though that code was written correctly and had no direct connection to storage.

Q5. Explain why refreshing the page appeared to "fix" the problem, even though the underlying bug was still there. (2 marks)

Show answer
Refreshing restarts the whole script from scratch, so the game looks like it's working again from round 1 — but the same unguarded localStorage call would throw and freeze it again as soon as another roll triggered a storage failure.

Q6. Which CT5-DPM-01 stage was missing when recordRoll was first written, and which stage caught the problem? (3 marks)

Show answer
Develop was incomplete — the function was written assuming storage always succeeds, with no plan for failure. Evaluate is what caught it: testing under a forced storage failure (by hand in the console, or by an automated script) revealed the freeze that normal testing wouldn't show.
Extension B–A

Q7 — Audit. Open source/dice-games-buggy.html and search for other localStorage.getItem or localStorage.setItem calls outside recordRoll. Find at least one more that is not wrapped in a try/catch, and explain what would visibly break if storage failed at that point. (3 marks)

Show answer
The font-preference toggle near the bottom of the script reads and writes localStorage.getItem('pro-dice-font') / setItem('pro-dice-font', name) with no try/catch. If storage failed there, it would likely break page load entirely (an uncaught error partway through setup), rather than just losing the saved font choice — a much more visible failure than a silently-reset stats tally.

Q8 — Fix and evaluate. Rewrite the font-preference code you found in Q7 using the same defensive pattern as recordRoll, then describe a test (like Section 5's console trick) that would prove your fix works. (4 marks)

Show answer
var savedFont = 'nunitosans';
try{ savedFont = localStorage.getItem('pro-dice-font') || 'nunitosans'; } catch(e){}
// ...inside applyFont():
try{ localStorage.setItem('pro-dice-font', name); } catch(e){}
Test: apply the same console override from Section 2 (localStorage.setItem = function(){ throw ... }) before the page finishes loading, then confirm the page still loads and the font buttons still work — clicking one just won't remember the choice next visit, instead of breaking the page. (This is in fact exactly how the real fixed file handles it — check source/dice-games-fixed.html to compare.)
