"It Looks Broken" — the Confirm Box Nobody Designed

A plain grey system pop-up interrupted an otherwise carefully styled page — and on some browsers, it didn't even appear at all. One built-in function quietly handed away control of the interface.

Artefact: Dice & Chance (MA4-PRO-C-01) Bug type: native vs custom UI DPM stages: Design & Develop
CT5-DPM-01 CT5-DES-01 Native vs custom UI

Not every bug is a logic error. This one is a design problem wearing the disguise of a broken button: the code ran exactly as written, but the decision to let the browser itself draw part of the interface was never actually made on purpose — it was just the fastest thing to type at the time.

1. The bug report

Player report
Clicking "Reset stats" pops up an ugly grey box that doesn't match the rest of the page at all — and on my school laptop it didn't show anything, the button just seemed to do nothing.

Two different symptoms, one root cause: a plain, unstyled dialog on most devices, and total silence on locked-down ones. Both come from the same line of code.

2. Investigate — hands-on

Try it yourself

Open source/dice-games-buggy.html and click either "Reset stats" button. Notice how the pop-up looks completely different from every other button, card and message on the page — it's drawn by the browser, not by this page's CSS.

Now open Developer Tools (F12), go to the Console, and paste this line to simulate a sandboxed browser context that blocks native dialogs (some managed school devices and embedded previews do exactly this):

window.confirm = function(){ return false; };

Click "Reset stats" again. What happens now? Does it look any different from a genuinely broken button?

3. Root cause: confirm() hands over control

The reset button used JavaScript's built-in confirm() function, which hands control to the browser itself to draw a dialog:

dice-games-buggy.html (before — real code from the original file)
document.getElementById('pylResetStats').addEventListener('click', function(){
  if (confirm('Reset all recorded Push Your Luck roll data? This cannot be undone.')){
    resetStats('pyl');
    renderStats('pyl');
  }
});

This is quick to write, but it hands away three things at once:

What confirm() gives up

  • Can't be styled to match the page
  • Can be silently blocked by sandboxed browser contexts (some managed school devices, embedded previews)
  • Is a blocking call — it freezes the whole page until answered, rather than behaving like the rest of the interface

What a custom panel gives back

  • Styled with the page's own CSS — consistent every time
  • Can never be "blocked" — it's just HTML the page already controls
  • Non-blocking — behaves like any other button on the page
Concept for students — native vs custom UI, and why "it works on my machine" isn't proof: browser-native dialogs are convenient but hand away control of appearance and behaviour — and different browsers, devices and security policies treat them differently. A page that owns its whole interface is more predictable across every device it might run on.

4. The fix: the page draws its own dialog

The native confirm() call was replaced with a small custom confirmation panel built from ordinary HTML elements, already styled to match the rest of the page:

dice-games-buggy.html (markup added — real code from the fixed file)
<button class="action btn-outline" id="pylResetStats">Reset Push Your Luck stats</button>
<div class="msg-box bust" id="pylResetConfirm" style="display:none;">
  <p>Reset all recorded Push Your Luck roll data? This cannot be undone.</p>
  <button class="action btn-terracotta" id="pylResetConfirmYes">Yes, reset it</button>
  <button class="action btn-outline" id="pylResetConfirmNo">Cancel</button>
</div>
dice-games-buggy.html (JavaScript added — real code from the fixed file)
document.getElementById('pylResetStats').addEventListener('click', function(){
  document.getElementById('pylResetConfirm').style.display = 'block';
});
document.getElementById('pylResetConfirmYes').addEventListener('click', function(){
  resetStats('pyl');
  renderStats('pyl');
  document.getElementById('pylResetConfirm').style.display = 'none';
});
document.getElementById('pylResetConfirmNo').addEventListener('click', function(){
  document.getElementById('pylResetConfirm').style.display = 'none';
});

Instead of one call that either shows or doesn't, there are now three plain click handlers — open the panel, confirm, or cancel — each just toggling a display style on an element the page already owns. Nothing here can be blocked by a browser security policy, because nothing here asks the browser for anything.

5. Proving the fix

Try it yourself — confirm the fix

Open source/dice-games-fixed.html and repeat the exact same console override from Section 2: window.confirm = function(){ return false; };. Click "Reset stats." Does the panel still appear? Can you still click "Yes, reset it"? If the override has no effect at all, that's proof the fixed version never asks the browser for a dialog in the first place.

6. Practice questions

Foundation D–E

Q1. What built-in JavaScript function was used to ask "are you sure?" before resetting stats? (1 mark)

Show answer
confirm()

Q2. Give two reasons a native confirm() dialog can cause problems on different devices. (2 marks)

Show answer
Any two of: it can't be styled to match the page; it can be silently blocked in sandboxed/managed browser contexts; it's a blocking call that freezes the whole page until answered.

Q3. In the fixed version, what HTML element is shown and hidden instead of using confirm()? (1 mark)

Show answer
A <div> with class msg-box (id pylResetConfirm), toggled with style.display.
Core C

Q4. Explain why "it worked when I tested it" was not good enough evidence that the reset button was fine, given what you now know about confirm(). (3 marks)

Show answer
Different browsers, devices and security policies treat native dialogs differently. Testing on one device that allows confirm() to display normally gives no evidence about devices that block it — the button can look completely fine to the developer and appear broken to a player on a locked-down device.

Q5. The fix replaced one if (confirm(...)) call with three separate click listeners. Explain what each one is responsible for. (3 marks)

Show answer
The first (on the "Reset stats" button) shows the confirmation panel. The second (on "Yes, reset it") actually resets the stats and hides the panel. The third (on "Cancel") just hides the panel without resetting anything.

Q6. Which CT5-DPM-01 stage was really at fault here — and why is it Design rather than Develop, even though the visible fix is a code change? (2 marks)

Show answer
Design — the mistake was never deciding, on purpose, who should own the confirmation dialog's appearance and behaviour. Develop only carried out whatever was fastest to type; the actual decision (page-owned UI vs browser-owned UI) belongs to Design, and once it's made correctly, the Develop step follows naturally.
Extension B–A

Q7 — Audit. Search source/dice-games-buggy.html for any other native browser dialogs (alert(), confirm(), prompt()). Did the Dice Cricket game's reset button have the same bug as Push Your Luck's? What does that tell you about how thoroughly the original bug should have been searched for and fixed? (3 marks)

Show answer
Yes — Dice Cricket's "Reset stats" button used its own separate confirm(...) call with the same problem, because the two games' reset logic was written separately rather than sharing one function. This shows that fixing a bug in one place doesn't fix every occurrence of the same pattern elsewhere in the code — a thorough fix means searching for every instance of the risky pattern, not just the one a bug report happened to point at (the same lesson as Level 1's six magic numbers).

Q8 — Evaluate. Design a short test plan (3–4 checks) that a developer could run to convince themselves the custom confirmation panel behaves correctly in every case a native confirm() used to cover. (4 marks)

Show answer
Accept any reasonable plan; a strong answer includes: (1) clicking "Reset stats" shows the panel and does not reset anything yet; (2) clicking "Yes, reset it" clears the stats and hides the panel; (3) clicking "Cancel" hides the panel and leaves the stats unchanged; (4) opening the panel, then clicking "Reset stats" again without answering first, to check the panel doesn't stack or duplicate itself; (5) confirming the panel behaves identically with window.confirm overridden or blocked, since the fix should no longer depend on it at all.
