A White Box With No Text

The "Cancel", "Reset stats" and "Play Again" buttons all rendered as blank white boxes. The buttons weren't broken — they were working perfectly, just rendering white text on a near-white background.

Artefact: Dice & Chance (MA4-PRO-C-01) Bug type: CSS specificity DPM stages: Develop & Evaluate
CT5-DPM-01 CT5-DES-01 CSS cascade

This is the clearest example in the whole series of the difference between "my code has an error" and "my code has a bug." There was no typo. Every CSS rule did exactly what it said. The browser followed its rules perfectly — the rules themselves just didn't produce the result anyone intended.

1. The bug report

Player report
The "Cancel", "Reset stats" and — worst of all — "Play Again" buttons are just blank white boxes. I can't see any text on them at all.

This also explains the Level 2 complaint about "Play Again doesn't work" from a completely different angle: the button had been clickable the whole time. It was just impossible to see.

2. Investigate — hands-on

Try it yourself

Open source/dice-games-buggy.html. Find the "Reset stats" button under either game — it should look like a blank white box. Right-click it and choose Inspect to open DevTools on that exact element.

In the Styles panel, look for the color property. You should see it listed twice, from two different selectors — and one of them will have a line through it, showing the browser rejected it. Which selector wins? Is it the one written last in the stylesheet?

Buggy: white text on white
Fixed: ink text wins

3. Root cause: two rules, one property, one winner

Two style rules both try to set the text colour of the same button:

dice-games-buggy.html (real CSS, in file order)
button.action{
  /* ...other properties... */
  color: var(--white);   /* written FIRST in the file */
}

.btn-outline{
  background: var(--white);
  color: var(--ink);      /* written LATER — but loses anyway */
  border: 2px solid var(--line) !important;
}

Every browser resolves conflicting CSS rules using specificity, not the order they're written in. Each selector gets a score based on how precisely it targets an element:

SelectorWhat it meansSpecificity (IDs, classes, elements)Wins?
button.action1 element + 1 class(0, 1, 1)✓ WINS
.btn-outline1 class only(0, 1, 0)loses

button.action combines an element type and a class, which scores higher than a class alone — regardless of which rule appears later in the file. The buttons weren't broken; they were rendering exactly as instructed: white text, on a near-white background, which is functionally invisible.

Concept for students — the CSS cascade and specificity: when two rules target the same element and property, the browser doesn't pick "whichever was written last" — it calculates a specificity score for each selector and the highest score wins, regardless of file order. This is one of the most common sources of "my CSS isn't working" confusion in web development, and it's invisible until you know to look for it.

4. The fix: force the intended rule to win

One line, using !important to force the intended colour to win regardless of the specificity comparison:

dice-games-buggy.html (after — real code from the fixed file)
.btn-outline{
  background: var(--white);
  color: var(--ink) !important;   /* forces this rule to win the specificity conflict */
  border: 2px solid var(--line) !important;
}
A note on !important: it works here, but it's a blunt instrument — it overrides the normal cascade entirely, which can make future specificity conflicts even harder to untangle, since !important rules can only be beaten by other !important rules with higher specificity. A more surgical long-term fix would be raising .btn-outline's own specificity to match or beat button.action directly — for example writing the selector as button.btn-outline. Both fixes solve this bug; only one avoids planting a harder version of the same problem for later.

5. Proving the fix

Try it yourself — confirm the fix

Open source/dice-games-fixed.html, inspect the same button, and look at the color property in the Styles panel again. This time .btn-outline's color: var(--ink) !important should be the one shown as active (not crossed out) — and the button text should be clearly visible.

6. Practice questions

Foundation D–E

Q1. What did the "broken" buttons actually look like, and what CSS property caused it? (2 marks)

Show answer
They looked like blank white boxes with no visible text. The color property was set to white on a white/near-white background, making the text technically present but invisible.

Q2. Were the buttons still clickable while they looked broken? How do you know? (1 mark)

Show answer
Yes — this also explained the earlier "Play Again doesn't work" complaint from Level 2's investigation; the button worked the whole time, it just couldn't be seen.

Q3. Does the browser use the CSS rule that was written last in the file when two rules conflict? (1 mark)

Show answer
No — it uses specificity, a calculated score for each selector, regardless of file order.
Core C

Q4. Explain why button.action beats .btn-outline, using the specificity scores from Section 3. (2 marks)

Show answer
button.action combines an element type and a class, scoring (0,1,1). .btn-outline is a class alone, scoring (0,1,0). Since (0,1,1) is higher than (0,1,0), button.action's color declaration wins, no matter which rule appears first or last in the file.

Q5. Calculate the specificity of each selector below as (IDs, classes, elements), then state which one would win a conflict: #pylMsg vs div.msg-box.bust. (3 marks)

Show answer
#pylMsg = (1,0,0). div.msg-box.bust = (0,2,1) — one element, two classes. An ID always outranks any number of classes, so #pylMsg wins.

Q6. Why is "it was written later in the file" not a safe assumption when debugging a CSS conflict? (2 marks)

Show answer
Because the cascade resolves conflicts by specificity score first, not by order. A more specific rule written earlier will still beat a less specific rule written later — assuming otherwise is exactly what caused this bug to go unnoticed.
Extension B–A

Q7 — Evaluate. The real fix used !important. Explain one risk this introduces for future maintenance, and describe the alternative fix mentioned in Section 4 that avoids that risk. (3 marks)

Show answer
Risk: an !important rule can only be overridden by another !important rule with equal or higher specificity, so any future style conflict involving this property becomes harder to reason about and may require yet another !important — a pattern that compounds over time. Alternative: raise .btn-outline's own specificity to genuinely beat button.action, e.g. rewriting the selector as button.btn-outline (element + class, matching or exceeding the competing rule) so the cascade resolves it normally, without needing to force anything.

Q8 — Design a check. A future developer adds a brand-new button style, .btn-mint, using only a class selector like the original buggy .btn-outline. Describe a specific, repeatable check they could run before shipping it, to make sure it won't fall into the same invisible-text trap. (4 marks)

Show answer
Accept reasonable answers; a strong one includes: search the stylesheet for every other selector that already targets button elements (like button.action) and matching classes; calculate the specificity of the new rule against each of those; and visually render the button in the browser (not just read the code) to confirm the text colour actually appears against its background — since, as this whole level showed, correct-looking code can still fail visually. This mirrors the general lesson: don't trust that a rule "should" apply — check the computed result.
