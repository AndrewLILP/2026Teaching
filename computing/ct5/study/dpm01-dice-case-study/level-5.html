Dice & Chance · Iteration Case Study · Level 5 (Final)

Some Graph Data Is Not Displaying

The percentages next to the bars were correct. The reference line was correct. The coloured bars themselves simply never appeared — because of one CSS property that most developers forget even exists.

Artefact: Dice & Chance (MA4-PRO-C-01) Bug type: box model / display DPM stages: all five, completing the cycle
CT5-DPM-01 Box model display property

This is the last bug in the series, and it closes the loop on the whole case study. Like the CSS specificity bug in Level 4, nothing here was technically "wrong" — the browser did exactly what its rules say to do. The bug was in which HTML element was chosen, not in any single line being incorrect.

1. The bug report

Teacher report
The "Compare My Dice" tab shows a thin line for the expected 1-in-6 probability, but the coloured bars for each die's actual results never show up — even though the percentage numbers next to them look correct.

This is a genuinely confusing symptom: if the maths behind the percentages is right, why would the bar itself fail to draw?

2. Investigate — hands-on

Try it yourself

Open source/dice-games-buggy.html. Roll the dice a few times in both Push Your Luck and Dice Cricket, then open the "Compare My Dice" tab. You should see the thin dashed reference line, correct percentage text — and no coloured bars at all.

Right-click one of the (invisible) bars' area and Inspect. Find the element with class bar-fill in the HTML panel. Look at its style attribute — it already has a width set as a percentage. Now check the Computed tab in DevTools for that same element: what width does the browser say it's actually rendering at?

3. Root cause: <span> ignores width and height

The coloured bar is built from a <span> element, with its width set by JavaScript as an inline style:

dice-games-buggy.html (real markup, generated by JS)
<span class="bar-track">
  <span class="bar-fill forest" style="width:38.2%"></span>
  <span class="bar-ref" style="left:16.7%"></span>
</span>
dice-games-buggy.html (real CSS, before)
.bar-fill{ height:100%; border-radius:6px 0 0 6px; }
.bar-ref{ position:absolute; top:0; bottom:0; width:2px; background:var(--slate); }

<span> is an inline element by default. A core rule of CSS is that width and height are simply ignored on inline elements — they only apply to block or inline-block elements. The inline style="width:38.2%" was there, correctly calculated, and the browser threw it away, because inline elements don't have a settable width at all.

The dashed reference line (.bar-ref, also a <span>) worked correctly by accident: position: absolute automatically makes an element render as block-level, regardless of its tag or default display type. It never asked to be block-level on purpose — it just happened to get that behaviour as a side effect of a different property. The coloured bar had no such override, so its width was ignored the entire time.

Concept for students — the CSS box model and the display property: every HTML element has a default display value (block, inline, or inline-block) that determines which CSS properties actually take effect on it. Using the wrong element for the job — an inline <span> where a block-level bar was needed — produces code with no errors at all, because nothing is technically "wrong": the browser is doing exactly what the CSS rules say. The bug is in the choice of element, not in any single line of code.

4. The fix: force block-level rendering

One property, forcing the element to behave as a block so its width takes effect:

dice-games-buggy.html (after — real code from the fixed file)
.bar-fill{ display:block; height:100%; border-radius:6px 0 0 6px; }

Nothing else needed to change — the JavaScript was already calculating and setting the correct percentage the entire time. The bug was never in the logic that produced the number; it was in a single missing CSS declaration that stopped that number from having any visible effect.

5. Proving the fix

Rather than trusting the visual result alone, the real fix was verified by reading the rendered width of each bar directly from the page's computed styles after simulating rolls — confirming every bar had a real, non-zero pixel width proportional to its data, not just "looks right in one screenshot."

Try it yourself — confirm the fix

On source/dice-games-buggy.html, roll some dice, open the Compare tab, then paste this into the DevTools console:

document.querySelectorAll('.bar-fill').forEach(el => console.log(el.className, el.getBoundingClientRect().width));

Note the widths reported (likely 0). Now open source/dice-games-fixed.html, repeat the same rolls and the same console command. The widths should now be real, non-zero numbers matching the percentages shown on screen.

6. Practice questions

Foundation D–E

Q1. Which HTML element was used for the coloured bar, and what is its default display value? (2 marks)

Show answer
A <span>, which defaults to display: inline.

Q2. What CSS property was missing that caused the bar to have zero visible width? (1 mark)

Show answer
display: block (or display: inline-block) on .bar-fill.

Q3. Was the percentage number shown next to each bar correct or incorrect? What does that tell you about where the bug was NOT located? (2 marks)

Show answer
Correct. This tells us the bug was not in the JavaScript that calculated the percentages — the maths was right the whole time. The bug was purely in the CSS that rendered the bar.
Core C

Q4. Explain, in your own words, why setting style="width:38.2%" on a <span> has no visible effect unless something else changes. (3 marks)

Show answer
By default, <span> is an inline element, and CSS specifies that width and height are ignored on inline elements regardless of what value is set. The browser reads the inline style, recognises it as a width declaration, and discards it because the element's display type doesn't support sizing — it isn't an error, it's the inline display algorithm working as specified.

Q5. The reference line (.bar-ref) is also a <span>, but it rendered correctly without any display fix. Explain why. (3 marks)

Show answer
.bar-ref uses position: absolute, and an absolutely positioned element is automatically treated as block-level by the browser regardless of its tag or default display value. Its width applied correctly as a side effect of that positioning rule — not because anyone deliberately made it block-level.

Q6. Suggest one alternative fix to display:block that would also make .bar-fill's width apply, and name one visual difference it might cause. (2 marks)

Show answer
display: inline-block would also respect the width. The difference: inline-block elements can sit next to other inline content on the same line and have slight baseline/whitespace spacing quirks, whereas block always takes the full width available and stacks — though inside this already-constrained .bar-track container, the visible difference would likely be minimal.
Extension B–A

Q7 — Evaluate. Explain why "the bar looked fine in my one test screenshot" would have been insufficient evidence that this bug was fixed, and why reading getBoundingClientRect().width programmatically is stronger evidence. (3 marks)

Show answer
A single screenshot only proves the bar rendered with *some* width in *one* specific case — it can't confirm the width is proportional to the actual data across many different roll outcomes, and a lucky coincidence (or a human not noticing a subtly wrong size) could pass an eyeball check. Reading the computed width directly and comparing it mathematically to the expected percentage, across multiple simulated data sets, proves the relationship holds in general — not just that one bar happened to look okay once.

Q8 — Connect the series. Levels 4 and 5 both involve "correct code producing the wrong outcome." State the general principle that connects them, and explain why this is a harder category of bug to find than a bug like Level 1's magic numbers. (4 marks)

Show answer
Both bugs come from the browser correctly following a rule (CSS specificity in Level 4; the inline-element display algorithm in Level 5) in a way nobody intended. The general principle: valid code doing exactly what it was told can still produce an unintended result — there is no error message, no crash, and nothing "wrong" to search for in the traditional sense. This is harder to find than Level 1's magic numbers because a magic number is at least visible in the code as a repeated literal value; Levels 4 and 5 require understanding the browser's own internal rules (the cascade; the box model) well enough to predict that correct-looking code will behave unexpectedly, before ever seeing the bug happen.

None of the five bugs in this series were caused by a typo or an obviously broken line of code. Every one of them was valid code doing exactly what it was told, producing a result nobody intended. This is the difference between "my code has an error" and "my code has a bug." Real debugging is rarely about spotting a typo — it's about understanding why correct-looking code produces the wrong outcome, and that understanding is exactly what the Evaluate stage of CT5-DPM-01 exists to build: not "it looks fine now," but a test that would catch the problem again if it ever came back.
