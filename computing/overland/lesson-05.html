CT5-EVL-01
Warm-up

"It runs" isn't "it works"

A program with no errors can still be wrong. Yours might run start to finish without crashing, print sensible-looking numbers, and still fail to actually do what the brief asked for — the most common way this happens is a rule that only gets tested by accident, on the one path you happened to play.

Testing is the deliberate search for the paths you didn't happen to play.

Concept

Testing concepts

Every test you run this lesson has the same shape: a starting condition, an action, and a comparison.

Set up

Put the program into a known state — e.g. food at a specific low value.

→
Expected result

What should happen, decided in advance, based on the brief or the pseudocode.

→
Actual result

What the program actually does when you run it — compared directly against the expected result.

Deciding the expected result before you run the code matters. If you only look afterwards and think "yeah, that seems about right," it's very easy to talk yourself into accepting a wrong answer.

Technique

Desk-check with fixed rolls

Random events make hand-tracing hard — you can't predict a real dice roll. The fix testers use: pretend the rolls are fixed numbers you chose, and trace what should happen for exactly those rolls. Try this one by hand before checking the answer.

Starting state: food = 100, health = 100, distance = 0. Fixed rolls: Day 0 → 2, Day 1 → 9, Day 2 → 5. Recall from Lesson 4: rolls 1–3 trigger the river event (food −15), 4–5 trigger illness (health −20), 6 triggers a broken wheel, 7–10 trigger nothing. travel() always runs first (food −10, distance +20).

Using this in Grok Learning: to test your own program against fixed rolls, temporarily replace random.randint(1, 10) with a hard-coded number like roll = 2, run it, check the result, then change the number and run again. Delete the hard-coded line once you're done — it's a testing tool, not part of the finished game.

This is an extremely common gap between a plan and its implementation — plans and code drift apart unless you test against the plan, not just against "does it look like it's working."

Bug detective

Why does this "win" check sometimes never fire?

def check_win(state):
    if state["distance"] == 2000:
        return True
    return False

# travel() adds 30km per day at fast pace
    # 0, 30, 60, 90 ... 1980, 2010 — never lands on exactly 2000
== 2000 only matches the single exact value 2000. At the default pace, distance increases by 20 each day, so it happens to land on 2000 exactly (100 × 20). At fast pace it increases by 30 — and 2000 isn't a multiple of 30, so distance jumps straight from 1980 to 2010, skipping over the one value the check looks for. The loop's own < 2000 condition still correctly stops at 2010, but the win message never prints, because check_win() never returns True. This is exactly why Sprint A's original code used >= 2000 instead of == 2000 — a range comparison can't be skipped over the way an exact match can.

Peer playtesting

Swap seats with a partner. They play your game start to finish without your help — you're only allowed to watch. Afterwards, ask them:

  • At any point, did you not understand what the game was telling you?
  • Did anything happen that felt unfair, or like it came from nowhere?
  • Did you ever type something and the game responded in a way you didn't expect?
  • Would you play again? Why or why not?

Record their answers in your Project Notebook — this is evidence a machine test can't produce, because it's about whether a human actually understands your feedback text, not just whether the code runs.

Vocabulary

Words you'll need this unit

Click each card to flip it.

Test case Show definition
A specific starting condition, paired with the result you expect the program to produce from it — the basic unit of testing.
Expected vs actual Show definition
The core comparison of testing — what the code should produce (decided in advance) versus what it really produces when run.
Boundary value Show definition
A value right at the edge of a condition (e.g. exactly 2000, or 1999 vs 2000) — bugs cluster at boundaries far more than in the middle of a range.
Edge case Show definition
An unusual but valid situation your code needs to handle correctly — running out of health while food is still fine, for instance.
Regression Show definition
A bug introduced by a change that breaks something that used to work correctly — a reason to re-test old features after adding new ones.
Playtesting Show definition
Testing done by a real user experiencing the program for the first time — surfaces confusion and unfairness that automated checks can't detect.
