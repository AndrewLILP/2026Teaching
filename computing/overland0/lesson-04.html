Warm-up

A boring, predictable trail

Run your Sprint A build a few times. Notice anything? Every playthrough is identical — same food loss, same distance gained, same number of days. There's nothing to react to and no reason to play twice.

Two things fix that: random events that interrupt the routine, and a genuine player choice each day that changes the outcome. Both need code that can misbehave in new ways, so today also covers keeping that code safe when things don't go to plan.

Concept

The random module

Python's random module needs importing once, at the top of the file, before it can be used.

Example 
import random

roll = random.randint(1, 10)   # a whole number from 1 to 10, inclusive
print(roll)
random.randint(1, 10) is inclusive at both ends — it can return 1, it can return 10, and everything between.

The plan: each day, roll a number from 1–10. Low rolls trigger different events; a high roll means nothing happens. This gives you control over how often — and how severe — events are, just by choosing which numbers map to what.

Step 1

Write the events

STEP 1 A single function, one roll, three outcomes 
import random

def check_for_event(state):
    roll = random.randint(1, 10)
    if roll <= 3:
        print("The river crossing is rough — some food is lost!")
        state["food"] -= 15
    elif roll <= 5:
        print("Someone in the party has fallen ill.")
        state["health"] -= 20
    elif roll <= 6:
        print("The wagon wheel has broken! You lose a day fixing it.")
        state["days_passed"] += 1
    return state
Rolls 1–3 (30% chance) trigger the river event, 4–5 (20%) the illness event, 6 (10%) the wheel break, and 7–10 (40%) nothing happens. Adjust those thresholds to tune difficulty — moving the wheel-break cutoff from 6 to 8 would nearly triple how often it fires.
Note: every branch changes state a different way, but they all share one function and one return state at the end — a repeat of the pattern from Lesson 3's travel().
Step 2

Wire events into the loop

while state["distance"] < 2000 and state["food"] > 0:
    print(f"Day {state['days_passed']}: "
          f"{state['distance']}km travelled, "
          f"{state['food']} food remaining")
    state = travel(state)
    state = check_for_event(state)
Order matters here: travel() runs first so distance and food always update, then check_for_event() has a chance to add an extra hit on top. Swap the order and an event could fire before the day's baseline travel happens — not wrong, exactly, but a different design decision, and one you should make on purpose rather than by accident.
Design

Designing clear feedback

This game has no graphics — every piece of feedback is a line of text. That makes the wording of your print() statements a genuine user-interface design decision, not an afterthought.

Weak feedbackWhy it failsStronger version
print("event") Tells the player nothing about what happened or why it matters print("Someone in the party has fallen ill.")
print(state) Dumps raw data the player has to decode themselves print(f"Health: {state['health']}")
print("bad") Gives no sense of scale — how bad? print("Health dropped by 20.")

The rule of thumb: a player should be able to tell, from the text alone, what happened and how much it changed their situation — without reading your source code.

Step 3

Validating player input

The moment a player makes a real choice, your program has to handle the case where they type something you didn't expect. This is where CT5-SAF-01 comes in for a text-based game: safe handling of data means the program never crashes or behaves unpredictably just because of what a player typed.

Pseudocode 
FUNCTION getPaceChoice()
  SET choice TO INPUT
  WHILE choice NOT IN ["1","2","3"]
    DISPLAY "Enter 1, 2, or 3."
    SET choice TO INPUT
  ENDWHILE
  RETURN choice
ENDFUNCTION
Python 
def get_pace_choice():
    valid = ["1", "2", "3"]
    choice = input(
        "Pace — 1) Slow 2) Normal 3) Fast: ")
    while choice not in valid:
        print("Enter 1, 2, or 3.")
        choice = input(
            "Pace — 1) Slow 2) Normal 3) Fast: ")
    return choice

This loop keeps re-asking until the player gives a valid answer — it never lets bad input reach the rest of the program. That's the same guard-clause thinking from Lesson 3, applied to user input instead of a function's starting condition.

Bug detective

Why does this event function break the game?

def check_for_event(state):
    roll = random.randint(1, 10)
    if roll <= 3:
        print("The river crossing is rough!")
        state["food"] -= 15
    elif roll <= 5:
        print("Someone has fallen ill.")
        state["health"] -= 20
    # missing return statement here

while state["distance"] < 2000 and state["food"] > 0:
    state = travel(state)
    state = check_for_event(state)
check_for_event() never reaches a return state line. In Python, a function with no return gives back None — so state = check_for_event(state) replaces the whole state dictionary with None on the very first day. The next line that tries state["food"] crashes with a TypeError, because you can't index into None. This is the same bug pattern from Lesson 3's quick check, showing up for real.
Vocabulary

Words you'll need this unit

Click each card to flip it.

Module Show definition
A file of pre-written Python code you can use in your own program with import, instead of writing that functionality yourself.
Branching Show definition
Code that follows one of several possible paths depending on a condition — Python's if / elif / else chain.
Input validation Show definition
Checking that data entered by a user meets expected rules before the program uses it, rejecting or re-requesting anything that doesn't.
Probability Show definition
How likely an outcome is, often expressed as a fraction or percentage — a roll of 1–3 out of 1–10 is a 30% probability.
None Show definition
Python's value for "nothing here" — what a function returns automatically if it reaches the end without an explicit return.
Crash Show definition
When a program stops running unexpectedly because of an error it wasn't written to handle — good input validation prevents crashes caused by bad user input.
