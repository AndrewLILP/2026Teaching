Deconstruct a Unity 3D Pet Project

This world moves from a 2D Godot game (Year 9) to a real 3D game in Unity 6 and C#. Your pet gets a body in 3D space, and instead of clicking buttons on screen, a player-controlled character walks up to it and presses a key to interact — the same idea as Godot's ClickArea, expressed through a completely different mechanism. Over these two lessons you won't write a single line of C#. You'll read someone else's, trace how the project is organised, and record what you find. Lesson 3 is where your own Y10 Pet Brief begins.

The class-and-inheritance thinking you already know from Year 9 still applies here — a base Pet class, subclasses extending it, guard clauses at the top of every method. What's new this year is interfaces: a way of guaranteeing that several different objects — the pet, a food bowl, a toy — all respond to the same interaction, even though each one does something completely different underneath.

Analysis Task

Read the Project Like a Reviewer

Open the project in Unity 6 and answer every question below in your project notebook. Use full sentences — this is your evidence, not a checklist.

  1. Open the Player GameObject in the Hierarchy. What script is attached, and what happens when the player presses the interact key near an object?
  2. Find the IInteractable interface script. How many methods does it declare, and what do they return?
  3. Open Pet.cs. Which fields have [SerializeField] private in front of them? What does adding [SerializeField] to a private field actually change in the Unity Editor?
  4. Trace what happens when Interact() is called on the Pet. Which private method does it call, and what guard clause runs first inside it?
  5. Open FoodBowl.cs. It also implements IInteractable. Does its Interact() method do the same thing as the Pet's? What does that tell you about what an interface actually guarantees?
  6. Find the TextMeshPro element in the Canvas. What script updates its text, and when does that update happen?
  7. Note one design decision in this project you disagree with, or would do differently. Explain why.
Identifying & Defining

Scene Hierarchy

Unity organises a scene as GameObjects, and everything a GameObject can do comes from the Components attached to it — a Collider doesn't know how to update a stat, and a script doesn't know how to render a mesh. Each component does one job. Here's the hierarchy you should find in the starter project's main scene:

  • ▾ SampleScene
    • ▸ Player Character Controller PlayerMovement.cs — reads input, moves the character PlayerInteractor.cs — detects nearby IInteractable objects, calls Interact()
    • ▸ Pet (Prefab) Capsule Collider — "Is Trigger" ticked Animator Pet.cs — implements IInteractable, holds stats
    • ▸ FoodBowl (Prefab) Box Collider — "Is Trigger" ticked FoodBowl.cs — also implements IInteractable
    • ▸ Canvas HungerBar — UI Slider StatusText — TextMeshPro – Text (UI)
    • ▸ Main Camera CameraFollow.cs — tracks Player transform each frame

Notice that Pet and FoodBowl are two completely different GameObjects, with different components and different scripts — but both have a script that implements IInteractable. PlayerInteractor.cs doesn't need to know which one it's looking at; it just calls Interact() on whatever's nearby, and each object handles that call in its own way.

Interfaces as a systems-thinking idea A component is a bit like a class in general programming — it defines a set of built-in behaviours and properties. An interface goes one step further: it's a promise that any class implementing it will provide certain methods, without saying anything about how. Recognising that PlayerInteractor can treat a pet and a food bowl identically, purely because both promise an Interact() method, is exactly the kind of systems-thinking pattern that only comes from reading other people's projects — which is exactly what you're doing right now.
Identifying & Defining

C# at a Glance

You won't write C# until Lesson 5 — but reading it now, side by side with NSW structured English, will make the starter project's scripts make sense. C# looks different from GDScript on the surface — curly braces, semicolons, explicit types — but the underlying ideas are the same ones you already know.

Reading the interface

Structured English 
INTERFACE IInteractable
  FUNCTION Interact()
C# 
public interface IInteractable
{
    void Interact();
}

An interface never contains a method's actual logic — only its name and what it returns. It's a contract: anything that says : IInteractable after its class name must provide its own Interact() method, or the project won't compile.

Reading Pet's Interact() and Feed()

Structured English 
CLASS Pet IMPLEMENTS IInteractable
  hunger, alive

  FUNCTION Interact()
    CALL Feed()

  FUNCTION Feed()
    IF NOT alive THEN
      RETURN
    END IF
    SET hunger TO hunger + 20, max 100
C# 
public class Pet : MonoBehaviour, IInteractable
{
    [SerializeField] private int hunger = 50;
    [SerializeField] private bool alive = true;

    public void Interact()
    {
        Feed();
    }

    private void Feed()
    {
        if (!alive) return;
        hunger = Mathf.Min(100, hunger + 20);
    }
}

Two things worth annotating in your notebook. First, if (!alive) return; is exactly the same guard clause pattern from Year 9, just written on one line instead of across several — C# allows a single-line body without curly braces when there's only one statement. Second, notice [SerializeField] private: the field stays private, so no other script can reach in and change hunger directly, but [SerializeField] tells Unity to still show it in the Inspector so you can tune starting values without editing code. That's the real encapsulation step this year — Year 9's public attributes are gone.

Where does hunger actually change from outside? If hunger is private, how does the HungerBar know what value to show? It doesn't reach in and read the field directly — instead, Pet.cs exposes a small public method or property that returns the current value. You'll build exactly this in Lesson 5, but it's worth watching for as you read Pet.cs now: private data, with a deliberate, narrow public doorway to it.
