Identifying & Defining

Writing Your Y10 Pet Brief

The first four parts are identical in spirit to Year 9 — you're welcome to reuse your Year 9 brief's numbers if you're happy with them, or design something new now that your pet lives in 3D space.

Part 1 · Concept & Pitch

Name and species for the base class, plus one sentence you'd actually pitch to PixelPals. What does your pet look and feel like now that it's a real 3D character, not a sprite?

Part 2 · Stat System

Three core stats, each with a starting value and exactly which interaction changes it. Identical structure to Year 9, just written for a base class with private fields this time.

Part 3 · Win Condition

An ongoing state, exactly like Year 9 — for example, "all three stats stay above 70."

Part 4 · Lose Condition

A single, testable threshold — for example, "hunger reaches 0." You'll turn this into a C# method in Lesson 5.

Researching & Planning

Shared vs Unique

Exactly the same planning question as Year 9: what belongs in the base Pet class because every future pet type needs it, and what's left for individual pet types to define differently once subclasses begin in Lesson 7?

Every Pet Type Needs (Base Class)
  • Core stats every pet tracks, like hunger and social
  • A name, an alive flag, and the IInteractable implementation
  • Shared methods like Feed(), Interact()
Each Pet Type Might Differ (Future Subclasses)
  • How fast a stat rises or falls per interaction
  • An extra stat only that type tracks
  • A special method or animation only that type has

Interaction Design

This is new this year: more than one kind of object in your scene will implement IInteractable, not just the pet itself. Before Lesson 5, plan every object the player can walk up to and interact with.

Your Turn

List at least two objects that will implement IInteractable this term — your pet, plus at least one prop such as a food bowl, toy, or brush. For each one, write one precise sentence describing exactly what its Interact() method does. Two objects implementing the same interface should still be allowed to do completely different things — that's the whole point of using an interface rather than one giant class.

Researching & Planning

Core Loop & C#

Your Core Loop is the moment-to-moment cycle a player repeats — walk close, interact, a stat changes, the UI updates. It's the only Pet Brief section that becomes C# directly in Lesson 5, which is why it needs pseudocode, not just prose.

Structured English 
WHEN player presses Interact key near Pet
  CALL Interact()

FUNCTION Interact()
  CALL Feed()

FUNCTION Feed()
  IF NOT alive THEN
    RETURN
  END IF
  SET hunger TO hunger + 20, max 100
C# 
public void Interact()
{
    Feed();
}

private void Feed()
{
    if (!alive) return;
    hunger = Mathf.Min(100, hunger + 20);
}

The shape is the same one you've used since Year 9: an event triggers a method, a guard clause checks state before anything changes, then the stat updates. PlayerInteractor.cs (which you read in Lesson 1–2) is what actually detects the player is close enough and calls Interact() — your job in the brief is only the logic from Interact() downward.

Your Turn

Write the Core Loop for your second interactable object from the Interaction Design section above — in both structured English and C#, using Feed() above as your model. If its Interact() doesn't fit the guard-clause shape at all, explain why in a sentence — not every interaction has to change a pet's stats.

Hierarchy Plan

Sketch a first-draft scene hierarchy for your own pet, in your notebook, in the same style as the starter project you analysed in Lessons 1–2:

  • ▾ YourScene
    • ▸ Player Character Controller, PlayerMovement.cs, PlayerInteractor.cs
    • ▸ Pet (Prefab) Trigger Collider, Animator, Pet.cs — your fields go here
    • ▸ [Your second interactable] — fill in its components
    • ▸ Canvas — your bars and TextMeshPro elements go here

You don't need to change the overall shape — the starter project's structure already solves player movement and interaction detection. What's yours to design is what sits inside Pet.cs and your second interactable's own script.
