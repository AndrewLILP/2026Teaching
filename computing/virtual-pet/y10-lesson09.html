Producing & Implementing

Sprint 3 — Five Steps

Work through these steps in order. Test after each one. Steps 1–4 follow the exact shape from Sprint 2 — the code isn't repeated here, only what's different.

1
Duplicate & Extend
Scene + Class Setup

Duplicate Pet's prefab as your second pet type's prefab, swap the artwork. Create its own script with public class ... : Pet. Remove any leftover Pet.cs reference first.

Test it — before adding anything new, confirm Feed, Play and Clean already work, exactly as they did on Dog. Fix this before Step 2 if they don't.

2
Add Your Unique Attribute & Method
Extending

From your Shared vs Unique plan, add one new [SerializeField] private attribute and one new public method — guard clause first, stat change, then NotifyStatChanged(); last, exactly like Fetch() on Dog. Add a matching public read-only property too.

3
Override a Different Method
virtual / override

Dog overrode Play(). Choose a different inherited method to override this time — Feed() or Clean(). Remember virtual is set per-method, not per-class: whichever one you pick still needs virtual added to it in Pet.cs first, exactly as you did for Play() in Sprint 2, even though Play() is already virtual. Then use base.MethodName() plus one extra line, following the same shape.

4
Wire the New Button & Bar
UI Binding

Add the button and bar for your new attribute. Wire the button's On Click () in the Inspector, and create a new UI subclass — : PetUI, overriding UpdateUI() with base.UpdateUI() plus your new bar's line, the same pattern DogUI used.

5
Build a Second IInteractable Object
Interface Polymorphism

Every interactable so far has been a Pet or a subclass of it. IInteractable doesn't require that — any class can implement it, related to Pet or not. Create a FoodBowl GameObject with a trigger collider, and script it from scratch:

Structured English 
CLASS FoodBowl IMPLEMENTS IInteractable
  isFull

  FUNCTION Interact()
    IF NOT isFull THEN
      RETURN
    END IF
    SET isFull TO False
C# 
public class FoodBowl : MonoBehaviour, IInteractable
{
    [SerializeField] private bool isFull = true;

    public void Interact()
    {
        if (!isFull) return;
        isFull = false;
        Debug.Log("Bowl emptied!");
    }
}

Notice FoodBowl doesn't extend Pet — it only implements IInteractable, and it has to write its own guard clause from scratch since it inherits nothing. That's the point: PlayerInteractor.cs can call Interact() on either a Pet, a subclass, or this completely unrelated FoodBowl, and it never needs to know or care which one it's actually looking at.

Test it — interact with the bowl once and confirm the Console logs the message; interact again immediately and confirm nothing happens the second time.

🔍 Evaluation

For each test where the actual result didn't match the expected result, write:

  1. What went wrong (the bug)
  2. What you changed to fix it (the fix)
  3. Whether the fix introduced any new problems (a regression)

A common bug at this stage: interacting with the FoodBowl throws a NullReferenceException in the Console. This usually means PlayerInteractor found the trigger collider but the FoodBowl script itself wasn't actually attached to that GameObject — check the Inspector, not the collider settings, first.
