Studio memo: "Before PixelPals takes any pitch seriously, we want proof your team understands what makes a digital companion feel alive — not just that you can draw a sprite. Play the demo pet below. Question every decision the designer made. Your own Pet Brief in Lesson 3 needs to be built on evidence, not guesswork."

Over this term you'll design and build your own virtual pet in MakeCode Arcade — a block-based game engine you may already have used. A virtual pet is a small system: a sprite that represents a living thing, a handful of attributes that change over time, and a set of actions the player can take to keep those attributes healthy. Simple rules, but they only feel alive when the numbers underneath are designed carefully.

Analysis Task

Play the Demo Like a Reviewer

Open the demo and play it for at least five minutes. Answer every question below in your project notebook. Use full sentences — this is your evidence, not a checklist.

  1. What are the pet's attributes (the numbers that change over time)? Name all of them.
  2. What actions can the player take, and which attribute does each one change?
  3. Watch one attribute closely. Does it drift on its own over time, or does it only change when the player acts?
  4. What happens to the sprite when an attribute gets very low or very high? Describe exactly what you see.
  5. Try to break it — keep pressing one action over and over. Does any number go below 0 or above 100? What happens if it tries to?
  6. Look at the variables list in the code editor. How many variables are there, and do their names make sense to someone who didn't build the project?
  7. Note one design decision in this pet you disagree with, or would do differently in your own. Explain why.
Identifying & Defining

Anatomy of a Pet System

Every virtual pet, no matter how simple or complex, is built from the same three ingredients: variables that store the pet's current state, events that let the player change that state, and a critical value — a threshold the pet reacts to.

Input

Player presses the Feed button

→
Process

hunger variable increases, clamped so it never goes above 100

→
Output

Sprite image and stat bar update on screen

A variable stores a number — hunger, energy, happiness. Every one of these should live somewhere between two limits, usually 0 (a critical need) and 100 (fully satisfied). Without a lower and upper limit a variable can drift into meaningless territory: hunger of −40 or happiness of 900 doesn't mean anything to the player. Keeping a variable inside its limits is called clamping, and you'll build it into every action you write.

Variables as a systems-thinking idea Three separate variables — hunger, energy, happiness — don't act alone. In a well-designed pet, one attribute getting critically low affects another: a starving pet loses energy faster, or a tired pet can't stay happy. Recognising that attributes influence each other, not just the player, is a systems-thinking skill you'll build on through every World of this studio.

Blocks at a Glance

You won't place blocks until Lesson 7 — but reading structured English side by side with what the MakeCode blocks will look like now will make the demo project's logic make sense.

Reading a feed action

Structured English 
WHEN Feed button pressed
  SET hunger TO hunger + 20
  IF hunger > 100 THEN
    SET hunger TO 100
  END IF
  UPDATE stat display
MakeCode Blocks
on button A pressed change hunger by 20 set hunger to Math.min(100, hunger) call updateStatDisplay()

The Math.min(100, hunger) block is doing the clamping you read about above — it compares two numbers and keeps the smaller one, which stops hunger ever going above 100. Find this exact pattern in the demo project's Feed script now — you already noticed what happens at the limit in Question 5.

Reading the drift-over-time loop

Structured English 
REPEAT FOREVER
  WAIT 5 seconds
  SET hunger TO hunger − 1
  IF hunger < 0 THEN
    SET hunger TO 0
  END IF
END REPEAT
MakeCode Blocks
forever pause 5000 ms change hunger by −1 set hunger to Math.max(0, hunger)

This is why hunger falls on its own even if the player does nothing — the forever block runs continuously in the background, exactly like the answer you gave in Question 3.
