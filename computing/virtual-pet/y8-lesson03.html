Identifying & Defining

Your Brief

Studio memo: "A save file is a promise to the player — close the program, come back tomorrow, and your pet should be exactly as you left it. Before any of your team writes save or load code, we need to see precisely what that promise covers. Guessing at save data once you're mid-build is how save files end up corrupted."

Quick reminder before you start: hunger still means how fed your pet is — Feed raises it, time lowers it, and 0 means starved. Every number in your brief should follow the same "low is bad" logic unless you have a specific reason to design it differently.

Identifying & Defining

Writing Your Y8 Pet Brief

The first four parts are identical in spirit to Year 7 — you're welcome to reuse your Year 7 brief's concept and numbers if you're happy with them, or design something new now that you're not limited to sprite-based visuals.

Part 1 · Concept

Name and species, same as before. Since there's no sprite this term, add one or two sentences describing how your pet would be described in text when the player checks its status — what does status actually print?

Part 2 · Three Core Stats

Hunger, energy, happiness (or your own names), each with a starting value and the command(s) that change it — identical structure to Year 7, just no sprite to react.

Part 3 · Win Condition

An ongoing state, exactly like Year 7 — for example, "all three stats stay above 70."

Part 4 · Lose Condition

A single, testable threshold — for example, "hunger reaches 0." You'll turn this into Python later on this page.

Researching & Planning

Planning What Gets Saved

Your pet's save file will be a small piece of JSON — a text format for storing named values, which Python can read and write with almost no extra code. Every variable in your brief that should still be true tomorrow needs a matching key in the save file.

{ "hunger": 50, "energy": 50, "happiness": 50, "[customStat]": 50, "gameState": "playing" }

Notice gameState is saved as text in quotes ("playing"), while the stats are saved as plain numbers, no quotes — JSON keeps the same True/False and text/number distinctions Python itself uses. This is also exactly the reasoning from Year 7 for why gameState was a text variable in the first place: a handful of named states reads far more clearly than a number code, in a save file just as much as in a program.

Not everything needs to be saved Anything that resets sensibly every time the program starts — like a temporary message on screen — doesn't need a save key. Deciding what's state (must persist) versus what's display (can be rebuilt fresh) is itself a design decision worth writing into your brief.
Researching & Planning

Pseudocode to Python

In Year 7, your pseudocode's IF/THEN/ENDIF became a shape of MakeCode blocks. This term it becomes real Python syntax directly — no translation step in between.

NSW Pseudocode 
IF hunger ≤ 0 THEN
  SET gameState TO "gameOver"
ENDIF
Python 
if hunger <= 0:
    gameState = "gameOver"

Python drops THEN and ENDIF entirely — the colon (:) after the condition takes the place of THEN, and indentation (four spaces, consistently) takes the place of ENDIF. Everything indented under the if line is what runs when the condition is true; the first line back at the original indentation is where the IF block ends. Get the indentation wrong, and Python will either run the wrong lines or refuse to run at all.

  1. Concept: pet name, species, and how it's described in a text status check.
  2. Three core stats with starting values and which command(s) change each one.
  3. Win condition and lose condition, each specific and testable.
  4. Save data plan: every JSON key your save file needs, following the example format.
