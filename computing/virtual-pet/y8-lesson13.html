Producing & Implementing

Building save_game()

Python's built-in json module converts a dictionary straight into the JSON format you planned. Add import json as the very first line of your file, above your variables.

save_game()

def save_game():
    data = {
        "hunger": hunger,
        "energy": energy,
        "happiness": happiness,
        "[customStat]": [customStat],
        "game_state": game_state
    }
    with open("save.json", "w") as file:
        json.dump(data, file)
    return True

data is a Python dictionary — a collection of key/value pairs, which is exactly what JSON itself looks like. with open("save.json", "w") as file: opens the file for writing ("w"); everything indented underneath runs while the file is open, and Python closes it automatically the moment that block ends — even if something goes wrong partway through. json.dump(data, file) does the actual conversion, turning your dictionary into the JSON text you planned back in Lesson 3–4.

Building load_game()

Loading is the reverse of saving — but with one problem saving never has: the very first time your program ever runs, save.json doesn't exist yet. Opening a file that isn't there normally crashes a Python program outright.

load_game()

def load_game():
    global hunger, energy, happiness, [customStat], game_state

    try:
        with open("save.json", "r") as file:
            data = json.load(file)
        hunger = data["hunger"]
        energy = data["energy"]
        happiness = data["happiness"]
        [customStat] = data["[customStat]"]
        game_state = data["game_state"]
        return True
    except FileNotFoundError:
        return False   # no save yet — keep the starting values

try / except is a new kind of guard — instead of checking a condition before acting like your other guard clauses, it attempts the risky action first and catches the specific problem if one occurs. FileNotFoundError names exactly the error Python raises when a file doesn't exist, so only that specific problem gets caught; any other kind of error would still stop the program, which is exactly what you want.

Same shape, same idea as every guard so far Whether it's "if hunger ≥ 100" or "except FileNotFoundError", the pattern is identical: detect the case where the normal path doesn't apply, and handle it deliberately instead of letting the program behave unpredictably.

Wiring It Into the Program

Two changes to your file's final section, just above the loop.

Just above while running: — runs once, at startup

loaded = load_game()
if loaded:
    print("Welcome back! Your save was loaded.")
else:
    print("No save found — starting a new pet.")

New branch inside the loop's if/elif chain

elif command == "save":
    save_game()
    print("Game saved.")

load_game() is called exactly once, before the loop begins — loading is a startup action, not something that should happen every cycle. save_game(), by contrast, lives inside the loop as a player command, exactly like feed or play, since the player should be able to save whenever they choose.

Test It Now — Three Checks

Check 1, first run: if save.json already exists from earlier testing, delete it, then run your file and confirm you see "No save found."

Check 2, save and reload: type feed, then save, then quit. Run the file again — confirm you see "Welcome back!" and that status shows the raised hunger value from before, not the original starting value.

Check 3, a broken save: open save.json in a text editor, delete a random character to make it invalid, and run your file again. If it crashes instead of handling the error, your except block needs a second look — a genuinely broken file is a different problem from a missing one, and it's worth noting which errors your current code does and doesn't catch.
