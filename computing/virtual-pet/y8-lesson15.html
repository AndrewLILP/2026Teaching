Boundary Testing Your Functions

A boundary value is a value sitting exactly on the edge of a condition — where an off-by-one mistake (using > instead of ≥, for example) would actually show up. Testing the middle of a range proves almost nothing; testing the edges proves the guard clause is exactly right.

A Bug Your except Doesn't Catch

Lesson 13–14's except FileNotFoundError only catches one specific problem: a file that doesn't exist. A file that exists, and is valid JSON, but is missing a key your code expects, is a completely different situation — and your current code doesn't handle it.

Discovery Task

Open your save.json in a text editor. Delete one entire line — the "energy" key and its value — making sure the file is still valid JSON (check your commas). Run your program. Watch what happens carefully, and note the exact error message.

Traceback (most recent call last):
  File "pet.py", line 41, in load_game
    energy = data["energy"]
KeyError: 'energy'

A KeyError happens when code tries to look up a dictionary key that isn't there — in this case, because a human edited the file by hand and removed it. Your except FileNotFoundError line does nothing here, because the file was found and opened just fine; the problem only appears once your code tries to read a key that's missing.

You're not expected to fix this yet Recognising and accurately describing a bug is the Lesson 15–16 skill — fixing it (most simply, by catching KeyError as a second except case) belongs in Lesson 17–18. Write this up as your first real bug report below.

Peer Testing

Swap your pet.py file with a partner — not your save file, just the code. Someone reading your program for the first time will try things you never considered, precisely because they don't already know how it's meant to be used.

Your Turn

Run your partner's program without reading the source code first — treat it exactly like a player would. Try: typing a command in capital letters, pressing Enter with nothing typed, typing a command word with a typo, and running the boundary tests from earlier on their functions instead of your own. Record anything that behaves unexpectedly, however minor.

Testing & Evaluating

Writing a Bug Report

A bug report that just says "it's broken" is nearly useless to whoever has to fix it — including future you. Use this exact structure for every bug you find today, starting with the KeyError from Lesson 15.

Steps to Reproduce
The exact, numbered actions that trigger the bug — specific enough that someone else could follow them and see the same failure.
Expected Result
What should have happened, based on the brief or the design.
Actual Result
What actually happened instead — the exact error message or wrong behaviour observed.
Severity
Minor (cosmetic, doesn't stop play), Major (breaks a feature), or Critical (crashes the whole program).
