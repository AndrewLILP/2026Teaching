Deconstruct a Godot Pet Project

This world moves from a console Python program (Year 8) to a real 2D game built in Godot 4 and GDScript. Your pet gets a body on screen, buttons a player can click, and stats that change visually — not just a printed status line. Over these two lessons you won't write a single line of GDScript. You'll read someone else's, trace how the project is organised, and record what you find. Lesson 3 is where your own Y9 Pet Brief begins.

Analysis Task

Read the Project Like a Reviewer

Open the project in Godot 4 and answer every question below in your project notebook. Use full sentences — this is your evidence, not a checklist.

  1. Open the pet scene in the Scene panel. What is the root node, and what type is it?
  2. Find the node that shows the pet's picture on screen. What node type is it, and how does it change when the pet's mood changes?
  3. Open the script attached to the pet. Find the function called feed(). What is the very first thing it checks before changing anything?
  4. Find the Timer node in the scene. What function runs every time it times out, and what does that function do to the pet's stats?
  5. Find one place a signal connects a button to a function — for example, what happens when the Feed button is clicked. Which node sends the signal, and which function receives it?
  6. Look at the project's folder structure in the FileSystem panel. What organisation choices has the original developer made — are scenes, scripts and art kept in separate folders?
  7. Note one design decision in this project you disagree with, or would do differently in your own game. Explain why.
Identifying & Defining

Scenes, Nodes & the Scene Tree

Everything in Godot is built from two ideas: nodes and scenes. A node is a single building block — a sprite, a collision shape, a timer, a piece of UI. A scene is a group of nodes arranged in a tree, saved together as one reusable unit. Your whole game is a tree of scenes, each one a tree of nodes.

Here's a simplified version of the scene tree you should find in the starter project's pet scene:

Pet (Node2D) ├─ AnimatedSprite2D // the pet's on-screen body ├─ ClickArea (Area2D) │   └─ CollisionShape2D ├─ StatTimer (Timer) // ticks every few seconds └─ UI (CanvasLayer)    ├─ HungerBar (ProgressBar)    ├─ FeedButton (Button)    ├─ PlayButton (Button)    └─ CleanButton (Button)

Notice that Area2D is used for the click target — it detects overlap (a click or tap) without physically blocking anything, exactly the same job it does for a collectible in a platformer. Timer is a node type built specifically to fire automatically after a set interval, which is what drives stat decay without you writing a loop yourself.

Nodes as a systems-thinking idea A node type is a bit like a class in general programming — it defines a set of built-in behaviours and properties. When you drag a Timer into your scene, you're not writing a countdown loop from scratch; you're using an existing system and adding your own logic on top of it. Recognising which built-in system already solves part of your problem is a core systems-thinking skill — and it only comes from reading other people's projects, which is exactly what you're doing right now.
Identifying & Defining

GDScript at a Glance

You won't write GDScript until Lesson 5 — but reading it now, side by side with NSW structured English, will make the starter project's script make sense. GDScript looks close to the Python you used in Year 8: indentation matters, and there are no curly braces.

Reading the feed method

Structured English 
FUNCTION feed
  IF NOT alive THEN
    RETURN
  END IF
  SET hunger TO hunger + 20, max 100
  EMIT stat_changed signal
GDScript 
func feed():
  if not alive:
    return
  hunger = min(100, hunger + 20)
  emit_signal("stat_changed")

The if not alive: return line is a guard clause — a check right at the top of a function that stops everything else in it from running if the condition isn't met. You'll see this exact pattern at the start of almost every method you write on your own pet, protecting it from actions that shouldn't happen once it's no longer alive.

Reading the stat-decay Timer

Structured English 
WHEN StatTimer times out
  SET hunger TO hunger - 5, min 0
  IF hunger ≤ 0 THEN
    SET alive TO False
  END IF
GDScript 
func _on_stat_timer_timeout():
  hunger = max(0, hunger - 5)
  if hunger <= 0:
    alive = false

This is a signal — Godot's version of an event. The StatTimer node emits a timeout signal every time it counts down to zero; the function _on_stat_timer_timeout receives that signal and reacts to it, without you ever calling the function yourself. Godot connects a node's signal to a function for you, which is why the function name always starts with _on_ followed by the node and signal it's listening to.
