Your Brief

Studio memo: "PixelPals is building a whole catalogue of pet types, not just one. Before your team writes a single class, we need to see precisely what every pet type has in common, and what's allowed to vary. Guessing at the shared structure once you're mid-build is how class hierarchies end up a tangled mess."

Quick reminder before you start: your stats still follow the same "low is bad" logic from Year 8 — Feed still raises hunger, time still lowers it. The one thing that's different this term is where that logic lives: every value you'd have written as global hunger now lives as self.hunger, and it belongs to whichever pet object it's attached to.

Writing Your Y9 Pet Brief

The first four parts are identical in spirit to Year 8 — you're welcome to reuse your Year 8 brief's concept and numbers if you're happy with them, or design something new now that your pet is a proper object.

Part 1 · Concept

Name and species, same as before, but written for the base class — describe your pet type in general terms, not one single named pet. Add a sentence describing what a status() method should print.

Part 2 · Three Core Stats

Hunger, social, cleanliness (or your own names), each with a starting value and the method(s) that change it — identical structure to Year 8, just written as attributes and methods instead of variables and functions.

Part 3 · Win Condition

An ongoing state, exactly like Year 8 — for example, "all three stats stay above 70."

Part 4 · Lose Condition

A single, testable threshold — for example, "hunger reaches 0." You'll turn this into a Python method later on this page.

Researching & Planning

Shared vs Unique

Everything you've written so far in Parts 1–4 belongs to the base class — the one class every future pet type in your studio will be built from. Before Lesson 5, sort your ideas into two lists: what belongs in the base class because every pet type needs it, and what you expect individual pet types to eventually do differently.

Every Pet Type Needs (Base Class)
  • Core stats every pet tracks, like hunger and social
  • A name and an alive flag
  • Shared methods like feed(), status()
Each Pet Type Might Differ (Future Subclasses)
  • How fast a stat rises or falls per action
  • An extra stat only that type tracks
  • A special method only that type has
You're not building subclasses yet This lesson is planning only — you won't write class Cat(Pet): until Lesson 5. But every decision you make here about what's shared directly determines what goes in the base class versus what gets left for later, so it's worth getting right now rather than guessing mid-build.
Researching & Planning

Class Pseudocode to Python

Your NSW pseudocode gains two new markers this term: CLASS / ENDCLASS wraps a whole class, and METHOD / ENDMETHOD wraps one method inside it. Everything else — IF/THEN/ENDIF, SET ... TO — works exactly as before.

NSW Pseudocode — Class Convention 
CLASS Pet
  METHOD checkLose()
    IF hunger ≤ 0 THEN
      SET alive TO False
    ENDIF
  ENDMETHOD
ENDCLASS
Python 
class Pet:
    def check_lose(self):
        if self.hunger <= 0:
            self.alive = False

CLASS becomes Python's class Pet:, and METHOD checkLose() becomes def check_lose(self):. Just like Year 8's IF, both ENDCLASS and ENDMETHOD disappear in real Python — indentation marks where each block ends instead. Notice one more thing: the pseudocode never mentions self at all. Pseudocode simply assumes "the current pet's own value" whenever it names an attribute like hunger; Python just makes that assumption explicit by writing self.hunger every time.

This is a guard clause check_lose is doing something you'll see constantly from here on: checking a condition right at the top of a method, before anything else happens. This pattern — test first, act only if it's safe — is called a guard clause, and it's how every method in your base class will protect itself from running on a pet that's no longer alive.
