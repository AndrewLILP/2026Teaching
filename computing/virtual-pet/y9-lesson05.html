Building the Base Class

Your Pet Brief has a Core Loop written in structured English. This sprint turns it into real GDScript: "WHEN FeedButton pressed — CALL feed(); IF NOT alive THEN RETURN; SET hunger TO hunger + 20." By the end you'll have a complete, working base Pet class — the exact foundation Lesson 7 extends into your first pet-type subclass.

Your Brief

Studio memo: "Talk is cheap — PixelPals wants a working build. Your Pet Brief from Lessons 3–4 must be complete before you start: Core Loop, Stat System, Shared vs Unique, Win & Lose Conditions, Node/Scene Plan. Every step below assumes it's sitting open next to you."

Everything you build this sprint belongs to the base class only. Don't create Dog, Cat, or any other subclass yet — that's Lesson 7. Your job here is to make one solid, fully working Pet class that every future pet type will extend from.

Producing & Implementing

Sprint 1 — Five Steps

Work through these steps in order. Test after each one — don't move on until the current step behaves correctly.

1
Build the Pet Scene
Scene Setup

Create a new scene with a Node2D as the root, named Pet. Add an AnimatedSprite2D child for the artwork, a ClickArea (Area2D) child with its own CollisionShape2D, a StatTimer (Timer) child, and a UI (CanvasLayer) child with your bars and buttons — matching the scene tree from Lessons 1–2 and your own Node/Scene Plan section.

Set StatTimer's Wait Time to 5 seconds and enable Autostart in the Inspector, so decay begins the moment the scene runs.

2
Script the Base Class
Class Setup

Attach a new script to the Pet root node and save it as Pet.gd. At the very top, declare its class name so subclasses can extend it later, then declare a signal and your public attributes — using the starting values from your Stat System section:

class_name Pet
extends Node2D

signal stat_changed

var pet_name: String = "Fido"
var hunger: int = 50
var social: int = 50
var cleanliness: int = 50
var alive: bool = true

These are public attributes, exactly as your brief specified — any other script, or any future subclass, can read or change them directly. No getters or setters are involved.

3
Write feed(), play() & clean()
Methods

Add feed() below your attributes, following the guard-clause shape from your Pet Brief exactly:

Structured English 
FUNCTION feed
  IF NOT alive THEN
    RETURN
  END IF
  SET hunger TO hunger + 20, max 100
  EMIT stat_changed signal
GDScript 
func feed():
  if not alive:
    return
  hunger = min(100, hunger + 20)
  emit_signal("stat_changed")

Now write play() and clean() yourself, in exactly the same shape: guard clause first, then the stat change from your Stat System, then emit_signal("stat_changed") last. Every method in your base class follows this pattern — no exceptions.

4
Wire the Buttons & Stat Decay
Signals

In the Pet scene, select FeedButton, open the Node tab, and connect its pressed signal to the Pet script — Godot auto-generates _on_feed_button_pressed() for you. Fill it in with one line, feed(). Repeat for PlayButton and CleanButton.

Then select StatTimer and connect its timeout signal the same way, checking your Lose Condition inside it:

func _on_stat_timer_timeout():
  hunger = max(0, hunger - 5)
  if hunger <= 0:
    alive = false
  emit_signal("stat_changed")

Test it — click Feed, Play and Clean and confirm the Output panel or a temporary print() shows each stat changing. Wait a few seconds and confirm hunger drops on its own once StatTimer fires.

5
Update the UI from Signals
UI Binding

Your ProgressBar nodes shouldn't be set manually inside every method — that's what stat_changed is for. In Pet.gd, connect to your own signal inside _ready(), then write one function that pushes every stat to its bar:

func _ready():
  stat_changed.connect(_update_ui)
  _update_ui()

func _update_ui():
  $UI/HungerBar.value = hunger

Add the equivalent line for every bar you have. Test it — click each button and watch every bar move immediately, with no manual refresh needed anywhere else in your code.

Testing & Evaluating

Test the Base Class

Complete this test table in your project notebook. Write the actual result you observed — not what you expected to happen.

Test case Expected result Your actual result (write in notebook)
Press the Feed button once Hunger increases by 20, capped at 100; HungerBar updates immediately Record actual result →
Press Feed repeatedly until hunger reads 100 Hunger stays at 100, never exceeds it Record actual result →
Wait for StatTimer to fire, without clicking anything Hunger decreases automatically; HungerBar updates with no click needed Record actual result →
Let hunger reach 0 (or set it to 0 directly for testing) alive becomes false Record actual result →
Press Feed after alive is false Nothing happens — hunger doesn't change at all Record actual result →
Press Play and Clean buttons Their stats update the same way Feed did, capped correctly Record actual result →
🔍 Evaluation

For each test where the actual result didn't match the expected result, write:

  1. What went wrong (the bug)
  2. What you changed to fix it (the fix)
  3. Whether the fix introduced any new problems (a regression)

A common bug at this stage: hunger still changes after alive is false, because a stat-changing line was written above the guard clause instead of below it. Test 5 above exists specifically to catch this — if it fails, check the order of lines inside the method, not the guard clause itself.

✓ Sprint 1 — Checklist

Your project must:

  • Have a Pet scene matching your Pet Brief's Node/Scene Plan (Node2D, AnimatedSprite2D, Area2D + CollisionShape2D, Timer, CanvasLayer)
  • Have Pet.gd declaring class_name Pet extends Node2D with public attributes matching your Stat System
  • Have feed(), play() and clean() methods, each starting with a guard clause checking alive
  • Have FeedButton, PlayButton and CleanButton signals connected and calling the correct methods
  • Have StatTimer connected, decaying stats automatically and setting alive to false at your Lose Condition
  • Have UI bars updating live from the stat_changed signal, with no manual refresh needed
  • Have a completed test table in your project notebook (all six tests attempted)
