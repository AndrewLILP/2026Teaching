Producing & Implementing

Sprint 3 — Five Steps

Work through these steps in order. Test after each one. Steps 1–4 follow the exact shape from Sprint 2 — the code isn't repeated here, only what's different.

1
Duplicate & Extend
Scene + Class Setup

Duplicate Pet.tscn as your second pet type's scene, rename the root node, swap the artwork. Create its own script with class_name ... extends Pet. Remove any leftover Pet.gd reference first.

Test it — before adding anything new, confirm Feed, Play and Clean already work, exactly as they did on Dog. If they don't, fix this before Step 2.

2
Add Your Unique Attribute & Method
Extending

From your Shared vs Unique plan, add one new attribute and one new method — guard clause first, stat change, then emit_signal("stat_changed"), exactly like fetch() on Dog. Don't copy Dog's code directly; adapt the shape to whatever action fits this pet type.

3
Override a Different Method
Overriding

Dog overrode play(). Choose a different inherited method to override this time — feed() or clean() — using the same super.methodName() pattern plus one extra line underneath. Deliberately choosing a different method than Dog matters: it's what makes Step 5's discussion actually mean something.

4
Wire the New Button & Bar
UI Binding

Add the button and bar for your new attribute. Connect the button's pressed signal, and override _update_ui() with super._update_ui() plus your new bar's line — the same pattern Dog used for LoyaltyBar.

5
Wire Direct Click Interaction
Input Event

Every button click you've wired so far used a simple pressed signal. Clicking the pet's own sprite is different — ClickArea needs to detect a raw mouse or touch event, not a button being pressed. Select ClickArea, connect its input_event signal, and write:

Structured English 
WHEN ClickArea detects an input event
  IF event is a mouse click THEN
    CALL onPetClicked()

FUNCTION onPetClicked
  IF NOT alive THEN
    RETURN
  END IF
  PLAY a short reaction animation
GDScript 
func _on_click_area_input_event(viewport, event, shape_idx):
  if event is InputEventMouseButton and event.pressed:
    on_pet_clicked()

func on_pet_clicked():
  if not alive:
    return
  $AnimatedSprite2D.play("happy")

Notice _on_click_area_input_event receives three parameters — viewport, event, and shape_idx — instead of the empty parentheses you've seen on every other signal so far. Godot passes these automatically because an input_event signal can fire for many different kinds of input; checking event is InputEventMouseButton is how the function narrows that down to specifically a click.

Notice too that on_pet_clicked() still starts with a guard clause, even though it's purely cosmetic — no stat changes here at all. The pattern doesn't change just because the consequence is smaller: once a pet isn't alive, nothing should happen when it's clicked, animation included.

Where should this really live? You've added this directly to your second pet type for now. If it turns out every pet type wants the same click reaction, it belongs up in the base Pet class instead, where every subclass inherits it automatically — exactly the same reasoning you used back in Lessons 3–4 to decide what was shared versus unique.

🔍 Evaluation

For each test where the actual result didn't match the expected result, write:

  1. What went wrong (the bug)
  2. What you changed to fix it (the fix)
  3. Whether the fix introduced any new problems (a regression)

A common bug at this stage: clicking the pet does nothing at all, because ClickArea's Input → Pickable property is switched off in the Inspector by default on some Godot versions. If Test 4 fails silently with no errors printed, this is the first place to check.
